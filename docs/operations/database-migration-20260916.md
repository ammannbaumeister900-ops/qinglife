# 数据库基线与迁移操作说明

## 范围

`server/bootstrap/legacy-schema.sql` 只包含 41 个旧表的建表定义，不包含旧 SQL 的 INSERT、账号、客户资料或密码。自增起点统一为 1。新环境不会自动得到管理员账号；账号初始化应使用实际部署的受控流程。

`DatabaseMigration` 是显式离线工具，不随应用启动执行。它支持空库初始化和**已由该工具完整管理**的后续升级。它不会自动接管已有业务数据库，不会按手机号合并身份，也不会删除重复记录。

## 新建隔离环境

1. 准备 MySQL 8.0+ 的空数据库，并用受限部署账号连接；先检查连接指向正确环境。
2. 构建 `server/api`，取得 `box-web/target/box-web.jar`。在当前进程设置 `QINGLIFE_MIGRATION_URL`、`QINGLIFE_MIGRATION_USER`、`QINGLIFE_MIGRATION_PASSWORD`，不要提交这些值。
3. 运行 `scripts/migrate-database.ps1 -JarPath <构建产物路径>`。迁移顺序为纯结构基线，再按数字版本顺序执行 `server/migrations`，其中 V1.3.10 继续读取原资源目录文件。
4. 检查 `ql_migration_run`：每个文件记录标准化换行后的 SHA-256、running/complete 状态和完成时间。所有文件完整后再次执行应只校验并跳过。

工具在同一连接上持有数据库命名锁，避免两个部署器同时执行。没有用普通数据库事务假装回滚多条 DDL。某文件中断后会保留 running；下一次明确拒绝重放。文件校验和改变也会拒绝。**不得手工改状态或删除日志来绕过失败。**

## 已有 V1.3.10 数据库

本轮没有取得实际旧库的可验证快照，因此不能声称其升级和身份冲突处理已经验收。

1. 停止旧库写入，制作备份，并先恢复到独立演练库。保留数据库版本、备份校验和和恢复结果。
2. 对照实际表结构、索引、已有 `ql_schema_migration` 与原部署记录建立版本清单；文件存在不等于执行过。
3. 在演练库运行 `server/operations/preflight-v1.3.10.sql`。它只输出问题数量，检查身份重复/尾空格/长度、孤立绑定、订单关联与付款冲突、负卡余额、超额名额和缺失价格快照。零数量也不代表全部语义已验收。
4. 非零项必须逐类核对，记录处理理由和关联变化；不能批量删除、猜测合并或追改已结算金额。
5. 仅在确认 V1.3.10 及之前真实结构完整后演练 V1.3.11 唯一约束迁移。索引已存在时，应比较列、排序规则、完整长度和唯一性，不盲目再次 ADD INDEX。
6. 跑身份、报名和付款验收，完成恢复演练后，才确定正式升级脚本与停写窗口。当前工具会拒绝无新迁移日志的既有库；不提供强制接管开关。

这部分仍是旧库发布前的必做工作，不能以空库测试通过替代。

## 回滚与恢复

迁移前备份必须可恢复。失败时保留原错误和迁移日志，在另一个空数据库恢复备份并检查表、外键、业务关联及关键记录。恢复完成前不重启依赖新结构的应用。工具不执行 DROP DATABASE，不处理生产服务，也不自动恢复备份。
