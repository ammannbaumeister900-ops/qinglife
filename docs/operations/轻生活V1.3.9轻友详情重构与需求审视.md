# 轻生活 V1.3.9｜轻友详情重构与需求审视

## 已确认范围

本次交付详情页重构：核心卡片、真实参与统计、卡次余额、统一时间线、业务分栏和现有操作入口。沟通新建、待办管理、通用附件归档及身份纠错流程不在本次范围。

用户确认的新老口径：实际参加 0 期为新轻友，参加 1 期及以上为老轻友。同一期多天签到仅计 1 次，报名和付款不代表参加。

## 已交付

- 电脑端宽屏侧栏，手机端全屏详情；核心信息分层展示，姓名与小名分开，缺失资料显示“未记录”。
- 顶部展示首次与最近实际参加期次、实际参加次数、当前可用卡次、首次推荐人、首次来源、最近沟通和待办。
- 参与统计来自到场事实，按期次去重；优先使用逐日签到，兼容没有逐日记录的历史期次参与事实。
- 卡次从账户流水汇总；仅处于有效状态、有效日期范围内的账户计入当前可用余额。账户与流水分别展示。
- 默认时间线，支持报名参与、付款卡次、沟通回访分类；业务事实、轻友自述、观察、判断使用不同文字标识。
- 历史服务回访原文不自动分类，不改写；期次完成显示为“关联期次已结束”，避免等同于个人完成。
- 活动、付款与卡次、沟通与跟进、资料与图片五个业务视图；图片复用已鉴权的回访图片接口，显示回访时间。
- 编辑资料复用现有编辑流程；报名与付款跳转携带唯一轻友编号，可携带具体期次，避免同名轻友混淆。
- 手机号和历史身份线索使用现有脱敏显示值，不把微信昵称冒充微信号。

## 对需求的建议

1. **首次推荐关系永久保留历史，允许有原因地纠错。**“永久保留”应防止后续期次覆盖，不能让录错后的资料永远无法更正。后续纠错应记录原值、新值、理由、操作人和时间。
2. **新老身份和参加次数是派生数据。**按本次确认口径计算，不增设人工维护字段。活动期次结束、报名确认、付款成功均不能证明个人到场。
3. **卡次需要明确可使用范围。**不同卡类型若可使用项目不同，未来应按类型突出展示，不能让总余额暗示所有卡可互换。当前数据库没有冻结状态，本次不虚构冻结逻辑。
4. **事实、自述、观察和判断是来源类型，不是自动判定的真伪等级。**保留原文与记录人；有冲突时展示来源和日期，不自动覆盖。
5. **沟通与待办分开建模、联动操作。**未来建议以“写一条沟通，可选生成一个待办”完成，避免工作人员连续填两张长表。待办应支持负责人、到期日期、完成结果和关闭原因。
6. **单一主档案不等于按手机号自动合并。**历史手机号继续保存在身份线索表；重复档案需人工核对，并保留合并前关联和审计记录。
7. **通用附件作为下一步独立范围。**当前已展示回访图片；语音、文件、活动合照的上传、关联、权限与筛选需一起设计，不能先放一个没有完整行为的上传按钮。
