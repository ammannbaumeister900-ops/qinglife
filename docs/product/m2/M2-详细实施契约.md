# M2 冻结规则与详细实施契约（待工程实施审批）

依据：本轮用户冻结规则、正式当前工作树及真实表结构。覆盖上一版“待确认业务边界”。本文件及同目录SQL/JSON仅用于审查和隔离验证；没有正式资金服务、生产迁移或新模式写入实现。

## 1. 冻结口径

- 每位参营者独立应收、付款确认、结算、退款、卡次与占位；整单为汇总。
- 收款事实只记录一次，可分配给同订单多人；同人可多笔现金收款，或一个有效卡次账户。本期不做同人现金+卡次、多卡拼单或卡次折现。
- 退款由运营录入，可分次、部分或全部；申请/待处理/实际已退分开。退款不取消报名、不释放名额。
- 卡次代用仅限主报名人账户与同订单同行人；运营核实并记录依据、范围、持卡人、使用人。无用户自行授权流程。
- 旧整单默认legacy_batch，不摊金额/卡次，不改历史事实；participant资金写入默认关闭。
- 返卡沿用既有整笔consume→void与唯一轮次约束，返原账户；本期不引入同轮分次返卡。

## 3. 新旧状态与兼容读取

| 触发 | participant人员状态 | 占位 | 资金事实 |
|---|---|---|---|
| 新报名 | pending / unpaid / settlement pending | 0 | 无到账推断 |
| 收款登记/部分分配 | 仍pending，显示已分配/待结清 | 0 | 真实收款独立存在，不自动确认同行 |
| 足额或差额二次确认后结清 | 目标人员confirmed；money结算confirmed、payment paid | 每人1 | final_amount为该人员最终结清金额，关联全部有效分配 |
| 单一卡次确认 | 目标人员confirmed；pass轮次confirmed | 每人1 | 原持有人账户扣本人的使用次数，绑定实际使用人及运营核实 |
| 申请/待处理退款 | 报名与结算保持；refundState=requested/processing | 不变 | 额度被预留 |
| 实际部分/全部退款完成 | 报名仍confirmed；原付款事实仍paid，另列partial/full退款与净额 | 不变 | 原收款+独立退款事实同时可见，不将payment_status改成refunded导致掉席 |
| 原账户返卡 | 显示返卡事实；不自动取消报名 | 不自动释放 | 追加原consume反向void，唯一一次，账户状态/有效期不变 |
| 单独取消报名 | 明确操作目标人员，registration cancelled | 释放该人员席位 | 不自动退款；未结资金/卡次仍留待办及审计，不允许通过重报绕开未处理事实 |

重要：新模式名额按registration_status=confirmed计数，确认入口严格与资金/卡次结清同事务；退款/返卡不得隐式取消确认。旧模式继续原Policy的现金/卡次占位条件。仅改payment SQL仍会造成全额退款掉席，必须同时改Policy、汇总和取消重报检查。

兼容读取：
- legacy_batch仍取batch结算字段、原整单轮次与整单撤销；不伪造逐人分摊。
- participant逐人读registration与明细；新增refundState、grossReceived、refundReserved、refundedAmount、netReceived、passUsage、seatOccupied、canOperate等只读字段。
- 订单汇总独立orderSummary：total/pending/confirmed/cancelled/paid/pass/refund人数及gross/refunded/net金额，partial/all等新汇总标签只放新字段。旧字段保持既有枚举，不把partial写入旧数据库枚举。
- 小程序本人只读自己的人员资金及允许的原有订单联系人范围；代报名者不能据新接口读取同行人的私人材料、退款凭证或完整授权依据。
- 老客户端对participant的旧资金写入口一律409升级提示或423门禁关闭；不能自动落回legacy_batch批量更新。

## 4. 接口契约（均为拟实施，当前未上线）

共用：金额使用十进制字符串，最多10位整数/2位小数；operationId UUID、expectedRevision整数。范围由登录身份+动作权限+目标资源校验，不能信任客户端operatorId/customerId。所有新写默认423。JSON契约：[M2-contracts.json](M2-contracts.json)。

| 接口 | 输入摘要 | 输出/关键拒绝 |
|---|---|---|
| GET /life/registration/batch/{id}/finance | 订单ID | mode、人员应收/分配/退款/卡次/占位、订单汇总、可操作范围和revision |
| POST /life/registration/{id}/offline-receipt（既有） | 原报文继续给legacy；participant新增captureOnly语义，真实方式、金额、凭证及requestId | receiptId、actualReceived、allocationState、unallocatedAmount；实际到账capture独立事务。旧默认整单confirm不得触发participant |
| POST /life/registration/batch/{id}/receipt-allocations（拟新增） | receiptId、expectedReceiptRevision、operationId、lines[{registrationId,amount}]、reason | 一次有界最多50人/行；允许只分配部分，返回分配ID和余款，不自动全部确认 |
| PUT /life/registration/{id}/settlement（既有扩展） | mode=participant、money、finalAmount、allocationIds、expectedRevision、operationId、differenceConfirmed/differenceReason | 只确认此人；原应收与最终不同须二次确认；所选有效分配总额=finalAmount，其他人不变 |
| POST /life/registration/{id}/refund-requests（拟新增） | requestedAmount、allocations[{allocationId,amount}]、reason、operationId、expectedRevision | requested，原分配逐笔占额；金额总和相等且不超可退 |
| PUT /life/registration/{id}/refund-requests/{requestId}/processing（拟新增） | revision、operationId | processing，不算已退，不改占位 |
| POST /life/registration/{id}/refund-requests/{requestId}/payments（拟新增） | actualAmount、方式、实际时间、凭证、回单号、revision、operationId | 先保存真实退款fact，再独立归因事务；正常返回applied/completed；归因失败返回recorded_unreconciled及待核对，不丢实际退款 |
| PUT .../refund-requests/{id}/cancel 或 /fail（拟新增） | 原因、revision、operationId | 只有明确未发生实际退款时可取消/失败并释放预留；有事实/在途不明时拒绝，进入reconciliation_required继续占额 |
| POST /life/registration/{id}/pass-verifications（拟新增） | passAccountId、passUnits、scope、basis、operationId、revision | 由服务端确定持卡人和使用人；代用只限同订单主报名人账户，运营核实记录ID |
| PUT .../{id}/settlement，pass（既有扩展） | verificationId、一个passAccountId、passUnits、operationId、revision | 不接受cashAmount/多卡；锁账户核身份、有效期、余额、核实范围，扣卡/结算/确认/审计同事务 |
| PUT .../settlement/{settlementId}/revoke（既有扩展） | 原轮次、原因、operationId、revision | 新模式只返该人的原consume账户与次数；旧模式仍整单。不会隐式释放席位 |

差额与部分付款：quote≠final需明确二次确认；部分分配只是已到账，不能自动结清。多笔真实收款可以覆盖一个人的money轮次，不因“实收≠应收”重写或复制原到账。

退款金额：申请金额及归因合计锁内校验。正常实际确认金额等于已核实申请；若真实已退金额不同，必须保留实际事实并进入差异核对，不能为了通过校验改小实际流水。未归因异常会冻结受影响资金的新退款/反向分配，核实后追加处理，不能自动释放额度。

## 5. 金额、事务、幂等与并发

- 可分配余额=已核实该笔真实到账−有效allocate总额+有效reverse总额；退款不把钱重新变成可分配到账。
- 可退额度=原有效分配−已完成退款归因−requested/processing/reconciliation_required的预留；同人多分配逐笔计算，不用应收/报价作为退款上限。
- 反向分配不得冲销已绑定有效结算、已退款或正在预留的部分；原分配和反向均不可变。取消/退款/冲正是不同动作。
- 锁顺序统一：期次→订单→目标报名（排序）→原收款/分配（排序）→退款申请/实际事实→账户（排序）。先锁原资源再算SUM；所有竞争路径同序，包括取消/重报和已有批量入口。
- 人员确认、名额校验、结算轮次、funding、扣/返卡与操作审计同事务。capacity判断只加入本次待确认人员；重试不再次占位。
- capture实际到账/实际退款分别使用独立事务；归属失败保留事实，记录待核对，不伪装整体失败。没有真实付款回执不标completed。
- operationId全局唯一，规范化载荷hash含动作/目标/操作者；相同重试回原结果，异载荷409。revision过期409，不先改一半再校验。事务死锁只做有界同标识重试，不生成新资金事实。
- 现金、退款、代用、返卡须独立操作权限；代用至少同时具有原结算/卡次动作权限及核实权限，退款权限不能凭payment权限推定。缺省拒绝，审计记录操作者、对象、原轮次、原账、差异原因。
- 不以DDL CHECK冒充跨行SUM、同订单、主报名人、权限或最终名额的业务验证；隔离测试验证锁机制与契约，真正Service实现仍须下一批补集成/HTTP鉴权测试。

## 6. 最小界面改动

后台：既有报名名单增加每人应收/已分配/退款/卡次/占位列；收款对话框保留一次到账，增加人员分配表和未分配余额；每人保留明确“确认此人”按钮，差额核对为二次动作。退款显示可退、预留、已退与实际凭证，申请/处理中/完成分开；取消报名独立按钮。卡次选择限制一个账户，代用显示持卡人≠使用人及必填核实依据，不做轻友授权页面。旧整单保留原有操作提示，不伪装按人。

小程序：个人中心/报名列表读每人的付款及退款事实，整单只显示汇总；本人同伴身份及已有联系规则保留。未准备的未知数据不造0；旧模式标原整单记录，不平均拆分。报名入口、资格、价格和套餐次数由既有Policy/Pricing/PassService决定，不增交易渠道。

## 9. 必须执行的验收集合

| 用例 | 断言 |
|---|---|
| A确认、B待付 | 仅A confirmed，1席，B未付；整单partial只为汇总 |
| 一笔到账分多人/多次 | 原流水1条，累计分配≤实收；同人可多笔到账 |
| 差额/部分款 | 无二次确认不能结清；未结清不占席 |
| 部分、多次、并发退款 | 合计不超实收可退；申请占额，明确未发生取消释放；已发生事实不删除 |
| 实际退款与归因失败 | 退款fact保留，待核对，不能显示已完成；原收款不变 |
| 退款完成 | 报名confirmed与席位不变；另操作取消才释放 |
| 未核实/跨单代用 | 拒绝；合法同单核实后记录持有人、实际人、账户和次数 |
| 原账户返卡 | 不激活过期卡、不改有效期、仅一次反向流水 |
| 最后一个名额 | 同时确认仅一人成功，失败不留下结算/卡账半状态 |
| 并存与回退 | legacy原值和整单行为不变，participant旧入口拒绝，写开关关闭后读仍可用 |
| 权限与重试 | 越权/失效运营拒绝；重复同标识不重复钱/扣次/返次，异载荷409 |

隔离草案验证不代表这些接口已实现，也不代表真实资金/微信业务验收。结果和未覆盖项另见本目录交付记录。
## 10. 现有收款语义的兼容重点

现有QlOfflineReceiptService.capture已由运营核实实际到账，却写transaction.status=pending_confirmation；allocate成功后才写paid并整单确认。participant不得沿用这套“到账状态=整单结清状态”。拟实施分支在运营核实captureOnly后将新模式真实交易置paid，表示该笔实际到账已核实；allocationState/unallocatedAmount由分配明细独立计算，不更新同行人的付款/报名状态。legacy_batch仍保留原有pending_confirmation→paid流程。此分支尚未实施。

同时改所有依赖pending_confirmation判断“待分配/是否可再收款”的读取与操作门禁：新模式允许多笔实际到账，不因某一笔paid或一笔未分配而拒绝合法后续到账；未分配钱仍计入实际到账总额。participant已有分配/预留/退款时禁止复用旧reconcile覆盖原金额/归属，纠错须独立事实/审计与受控反向分配。不能自动把历史pending_confirmation转paid，也不能通过旧客户端补确认触发整单结算。

capture接口保留既有requestId与金额8位整数校验、receiptReference及附件规则；新增captureOnly仅用于participant。新增分配/结算/退款事实字段使用decimal(12,2)上限10位整数，但每笔到账入口原有上限不放宽。JSON capture为核心无附件载荷，图片仍原有最多3张、MIME/字节及私有存储流程，实施时继承现有BO验证，不建设第二个附件系统。

## 11. 剩余实施边界与待确认项

用户本轮冻结的多人、退款、运营核实代用、非混合、历史双模式规则全部按已确认需求处理；以下只影响例外/上线授权，不反推为新增批准需求：

- 退款与代用核实的具体运营角色、独立权限授予名单，由业务负责人确认；现有付款权限不默认拥有这两个动作。下一批实现先测试默认拒绝。
- 0元应收/全额免收是否需要新模式专门确认路径，需确定运营凭据和占位口径；当前拟money分配要求真实正额到账，不生成虚假0元收款来绕过。legacy既有路径不改，新模式例外确认前不开放。
- 实际退款由运营执行后记录，归因异常保留fact与待核对；涉及同一笔实际退款同时覆盖多人的回单，不在本轮“按人退款”冻结范围，未经另批不扩展为跨人退款池。
- 这批只有草案和SQL机制验证，正式权限/旧客户端拦截、事务失败重试、个人中心读取、所有新旧入口及资金真实业务验收，须下一批实现后验证，不宣称已通过。
