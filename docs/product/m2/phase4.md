## 界面与规则来源

沿用报名列表和 Element UI；participant 进入“订单详情”，legacy_batch 保留原操作，不暴露错误的整单付款、编辑或取消入口。订单详情按每人、到账分配、退款、卡次四个阅读区域组织；敏感操作使用小型确认表单。颜色使用深绿 #234b40、正文 #263e35、次级 #64726d、差异 #a25a17、危险操作 #ae3d35；普通阅读13–14px，摘要23px，使用现有按钮/表格/对话框，不引入新框架。

资金、占位、预留和卡次状态来自服务端。前端只格式化金额与汇总本次填写的退款行；不推导可退额度或自行改账。卡次confirmed即显示“卡次已结算 / 无现金欠款”，不按payment_status=unpaid显示欠款。退款、逐人取消、原账户返卡仍是独立操作。重报提示复用已有报名策略，仅提供只读提示；真正新报名仍检查期次、价格和名额，不恢复旧报名。

服务端只补充现有finance快照所需的姓名、客户/账户/当前轮次、到账凭证摘要、退款历史、每条分配可退余额与重报提示；没有新迁移或资金写入规则。卡次选项增加可选scope=self/same_order，由服务端确定本人/主报名人，保留原缺省legacy选择；仍需要life:pass:list，不自动授予权限。

## 操作与恢复

- 登记真实到账 → 按本笔余额分配给多位报名人 → 分别确认现金结清；也支持同一人多笔现金来源。
- 退款申请按原分配预留 → 可开始处理、取消申请、记录失败或登记实际退款。取消/失败必须明确核实未实际退付。多次部分退款使用独立申请；实际退款与申请差异保留事实和待核对状态，不提供擅自修正入口。
- 本人或同单主报名人卡次 → 运营填写核实依据 → 独立确认扣次/报名。未使用核实可撤销；已使用必须按原轮次返还原账户。历史显示使用人、持卡人、账户、营期和原扣返关联。
- 每次写入保留操作UUID、修订与原报文。提交前锁定按钮防双击，敏感动作二次确认。结果未知时锁定表单与关闭入口，只能原请求重试；浏览器刷新/关闭有提示。不要在未知结果时另开页面重新登记，重开浏览器后必须先查历史。
- 成功写入与刷新失败分开反馈。409引导刷新核对，403引导核对角色授权，401要求重新登录后查历史，423说明默认关闭。权限取服务端当前登录信息的交集，最终由API校验。
