# 轻生活内部工作人员移动工作台 MVP 产品需求文档 V1.0

日期：2026-09-09  
状态：产品设计稿，供范围确认与开发拆解；不是已实现功能说明。  
适用：在现有轻生活微信小程序中新增按权限开放的工作人员工作台。  
目标：工作人员在服务现场能找到轻友、处理报名付款和卡次、留下沟通及附件、安排下一步，轻友端同步看到自己的正确结果。

## 1. 决策依据与范围边界

### 1.1 已确认的产品方向

1. 复用现有小程序，在“我的”中增加“工作人员工作台”，仅有工作人员权限的账号可见；内部页面独立组织。
2. 小程序、电脑后台共用统一轻友档案和业务数据，不新建另一套人员、报名或卡次账。
3. 电脑后台继续负责复杂期次配置、历史导入、身份冲突处理、账号权限和审计。
4. 老轻友价格按实际参与人判定：本人完成过至少一期轻体营。购买人、邀请人或代报名人的经历不能替代参与人的资格。
5. 原有真实历史打卡内容保留，不因建设内部工作台而删除，也不默认转为工作人员可见资料。

本方案调整《9月15日产品交付范围 V1.1》中内部端采用独立移动 H5 的载体建议，保留其统一档案与内部移动办公目标。《轻友统一档案产品设计 V1.1》也已提出授权角色进入同一品牌小程序的可能性。本期不再重复建设内部移动 H5。

### 1.2 本文的建议与待确认事项

页面结构、按钮组织、最小角色动作分配、异常流程及实施顺序为本次设计建议。涉及卡次商业规则、实际工作人员名单、敏感资料范围的部分，见第 13 节；不得在开发中猜测规则。

既有记录显示后续确认内部角色可查看全部期次，本文沿用该期次范围，不重新限制为“仅负责期次”。**能查看全部期次，不等于能查看所有私人内容或执行所有动作。**

### 1.3 首期定位

面向少量已授权工作人员的内部灰度版本。本文不承诺全部能力一定在 9 月 15 日前完成；是否交付由第 12 节验收判断。移动工作台只是完整交付的一部分，卡次、授权及导入等跨端配套不能被省略。

## 2. 用户、问题与成功目标

| 用户 | 典型场景 | MVP 要解决的问题 |
| --- | --- | --- |
| 运营工作人员 | 桃子、彩虹等接到电话或微信报名，活动现场接待 | 查到同一人；人工补报名；核实付款与卡次；记录沟通和待办 |
| 导游 | 公主、大海、军军等查看名单、接待及记录现场情况 | 看必要资料与参与安排；登记到场；留下带时间和作者的观察 |
| 管理员 | 开通账号、处理冲突及业务更正 | 控制权限；保证身份、账目与历史可追溯 |
| 财务职责人员 | 确认线下收款或纠正错误登记 | 核对付款对象和金额；记录实收与更正，不混同报名状态 |

上表人名为使用场景示例，不表示已经为该人员授权。期次“导游”标签只表达人员安排，必须另行关联工作人员账号，不能用标签文字授予权限。

验收目标：

- 从首页出发，工作人员 30 秒内找到指定轻友。
- 档案首屏看到最近参与、卡次余额及待办；未知信息显示“待核实”，不显示假零值。
- 纯文字沟通记录通常 1 分钟内完成；不把附件网络传输耗时混入输入效率。
- 在已定位正确报名或卡次账户、信息齐全时，付款登记或扣次通常 30 秒内完成。
- 从期次名单进入轻友档案不超过 2 次点击。
- 相同数据在轻友端和后台刷新后显示一致；不以本地模拟状态证明保存成功。

以上为产品验收目标，需由实际工作人员手机测试，不是已经实现的结果。

## 3. MVP 范围与非目标

| 范围 | 必须交付的最小能力 | 边界 |
| --- | --- | --- |
| 工作身份 | 账号绑定、权限入口、服务端校验、撤销访问 | 不开放自行注册工作人员 |
| 工作台 | 待报名、待付款、近期名单、回访、快速查人/记录 | 不做经营大屏和自动评分 |
| 轻友档案 | 搜索、基础资料、活动和交易事实、卡次、沟通附件、待办时间线 | 不堆满标签，不做健康画像 |
| 期次业务 | 统一名单、人工报名、确认、签到、受控改期 | 复杂期次编辑留电脑后台 |
| 收款 | 登记线下实际收款，保留更正原因与历史 | 不发起微信支付、退款或资金转账 |
| 卡次 | 查看账户、关联报名登记消耗、余额同步、更正追溯 | 不建设优惠营销或复杂储值系统 |
| 沟通附件 | 一句话摘要、图片/语音/文件、关联轻友和可选期次 | 不采集聊天记录，不转写、不生成 AI 摘要 |
| 回访 | 负责人、日期、动作、完成结果、关闭原因 | 不做自动营销触达或复杂任务流 |
| 跨端配套 | 本人卡次查询、真实授权、基础导入和审计恢复 | 不能仅完成移动页面便认定会议闭环通过 |

不进入首期：商城、在线支付、积分排行、社区重建、AI 档案问答、自动照片识别、自动微信消息、完整 21 天陪伴、离线资料库。已有轻友端感受和邀请保留，只修阻断问题，不在本项目中扩展。

## 4. 信息架构与入口

```text
现有小程序：我的
  └─ 工作人员工作台（授权后显示）
       ├─ 工作台：待办摘要、搜索、快速记录
       ├─ 轻友：搜索结果 → 档案 → 业务详情/快速记录
       ├─ 期次：期次列表 → 统一名单 → 报名处理/轻友档案
       └─ 我的：工作身份、权限说明、操作记录、返回轻友端

跨页面：回访列表与详情、报名详情、收款登记、卡次使用、附件预览
电脑后台：账号授权、期次复杂配置、卡次开户/调整、导入冲突、审计
```

内部四入口只在工作台区域使用，不改变原小程序“首页、轻体营、轻读、我的”四频道。进入内部区域显示明确的“工作人员”标识；“返回轻友端”恢复轻友界面，不撤销工作身份。

工作人员也可能是轻友，两种身份可以共存，但“我的私人记录”仍按本人身份查询，不能因切入工作模式扩大可见范围。

## 5. 页面需求

### W01 工作台首页

目标：打开即知道今天该做什么，并直接进入操作。

| 功能 | 功能描述 | 规则 |
| --- | --- | --- |
| 搜索轻友 | 顶部搜索框，支持称呼、姓名、手机号、轻友编号 | 同名列出可区分线索；不自动选中或合并 |
| 待确认报名 | 显示待确认数量和最早待处理事项，点击进入筛选名单 | 候补单独标识；不把所有未付款当作待确认 |
| 待付款 | 展示需线下付款且未完成登记的报名/订单 | 卡次结算不能误列为现金欠款；按订单展示时不得重复计数 |
| 近期活动 | 进行中优先，其次即将开始；卡片直达名单 | 日期、期数、人数与服务器一致 |
| 我的回访 | 逾期、今日、之后分组；默认负责人为当前人 | 有权限人员可切换团队范围，不能默认为所有人推送 |
| 快速记录 | 选择轻友后进入简记，可附期次和后续动作 | 从档案发起时自动带入该轻友 |

首期不把导入冲突、复杂改期审批和新增档案动态都堆在首页；冲突在电脑后台处理，移动端遇到冲突明确提示并保留待处理线索。空状态显示“暂无待处理”，失败显示“暂时无法加载”，不能把失败显示为零。

### W02 轻友搜索与列表

目标：快速找到正确的人，减少重复建档。

- 搜索支持姓名/称呼、手机号、轻友编号；在期次筛选下限定参加过指定期次的轻友。
- 列表显示称呼、脱敏手机号、城市、最近期次；新老状态按参与事实计算，历史不全时标注待核实。
- 首期筛选保留“指定期次、待回访”；复杂卡次到期、长期未沟通筛选后置。
- 手机号完整查看需对应权限，按需展开并记录访问；不默认整屏暴露号码。
- “新增轻友”先展示候选重复项；姓名相同或手机号相同只是线索，不直接合并。
- 必填常用称呼；其他基础字段按业务需要补充，未知不造值。缺少身份线索的人工建档不自动绑定微信账号。
- 历史手机号保留为线索，手机号变更不得抹除历史关系；争议身份转管理员核实。

### W03 轻友档案

目标：首屏看懂关键事实，向下追溯服务过程。

首屏：称呼/姓名、脱敏联系方式、城市、新老状态、首次/最近完成期次、完成次数、卡次余额、最近沟通和待回访；未核实历史与可用余额区分展示。

| 内容区 | 功能描述与目标 | 最小交互 |
| --- | --- | --- |
| 服务时间线 | 汇总报名、付款、参与、卡次、沟通、附件、回访，便于交接 | 倒序分页；按事实/沟通/附件筛选；点击查看原始详情 |
| 活动记录 | 查看历次报名、实际参与和取消/改期链路 | 点期次查看对应报名，不把报名次数当完成次数 |
| 卡次与收款 | 展示本人账户和相关结算事实 | 点账户查看流水；点报名查看实收，权限不足隐藏金额 |
| 沟通与附件 | 追溯谁在何时记录什么 | 新增简记、查看附件、查看更正历史 |
| 回访 | 查看待办和已完成结果，支持接续服务 | 新增、改日期/负责人、完成或关闭 |
| 授权摘要 | 展示可用的授权范围及版本状态 | 只读；工作人员不能代轻友随意勾选授权 |

固定主操作为“记录沟通”，次操作为“新增报名”；卡次扣减从明确报名进入。初版可用折叠区与统一时间线，不要求每个区独立大页面。

时间线区分：客观业务事实、轻友自述、工作人员观察。作者、发生时间、记录时间、来源、可见范围必须可追溯；主观观察不得变成系统认定的属性。小程序私人感受默认不汇入内部时间线。

### W04 期次列表与名单

目标：同一份名单承接小程序报名和人工补录，支持现场工作。

- 进行中、开放报名、已结束分组；显示期数、名称、日期、城市、导游及人数。
- 名单按实际参与人列行，显示姓名/称呼、报名状态、到场状态；金额仅按权限显示。
- 一笔多人订单有多个参与行，同时明确购买人和订单关系，不能把同行者合并成一个人。
- 支持待确认、候补、已确认、已取消及当日到场筛选；付款过滤仅授权人员可用。
- 行操作：看报名、进档案、登记签到；新增报名允许从当前期次发起。
- 日签到关联同一期次的明确活动日，登记签到/迟到/缺席；更正需原因，保留原状态。一次日签到不直接代表整期完成。
- 手机端不建设复杂活动模板、内容发布或批量导出。

### W05 人工报名与报名详情

目标：以正确参与人和期次建立唯一、可追溯的报名。

流程：选择已存在轻友或受控建档 → 选择期次 → 核对参与人、购买人、资格及结算方式 → 提交 → 返回真实报名结果。

- 默认单人快速补录；多人业务继续沿用现有订单/参与人关系，不另造平行模型。
- 同一参与人已有该期有效报名时进入现有报名，不重复创建；候补、已取消后的处理需按报名服务规则执行。
- 名额、报名窗口、期次状态以服务端为准；并发最后一个名额不得超售。特殊人工补录是否允许越过窗口见决策项，不默认绕过。
- 新老价格用实际参与人资格，沿用本期价格及订单快照；卡次结算另行核验账户，不把折扣金额折算成次数。
- 确认方式沿用期次自动/人工规则；确认报名与完成付款分开。
- 详情显示：期次、参与人、购买人、来源、首次推荐与本期推荐、报名状态、结算方式、相关付款/卡次、处理历史。
- 首次推荐关系永久保留；本期推荐与回归说明不能覆盖首次关系。

改期最小流程：选择目标期次 → 核查名额、重复报名及费用/卡次影响 → 确认更正原因 → 创建关联的新报名并保留原记录。首次版本不自动计算差价或退款；涉及已有付款/卡次的改期须进入管理员受控处理，未完成时显示“待处理”，不能只改状态便声称已转期。

### W06 线下收款登记与更正

目标：准确记录已经发生的线下收款，不在小程序内发起资金交易。

| 字段/动作 | 要求 |
| --- | --- |
| 核对对象 | 期次、订单/报名、购买人、参与人、应收金额醒目展示 |
| 实收金额 | 明确金额单位；合法金额校验；与应收不一致不能静默等同结清 |
| 收款方式与时间 | 沿用微信扫码、支付宝扫码、转账、现金、其他；时间可核实补录 |
| 确认收款 | 二次核对后提交，操作人由服务端记录；重复点击不产生重复交易 |
| 多人订单 | 明确本次登记影响整单还是个人，不能给整单重复收款 |
| 更正/撤销 | 有权限人员填写原因，原交易和变更历史保留；不是实际退款 |

首期不新增分期和复杂欠款台账。部分收款、优惠差额的处理口径必须确认后才能实现；未经确认时不允许以“已付款”掩盖差额。

### W07 卡次账户与使用登记

目标：现场能判断是否可用、登记一次使用，并让本人看到一致余额。

- 账户归属明确轻友；显示卡名称、核实状态、可用余额及已配置的有效期，不凭历史口述推算余额。
- 流水展示发放、使用、调整、撤销及原因、发生时间、操作人；历史来源和核实依据可追溯。
- 扣次必须关联明确参与人、有效报名和期次；展示扣次前/本次/扣次后余额。
- 同一次有效使用不能因双击、重试或两名工作人员操作重复扣减；余额不足或账户不可用时不得出现负余额。
- 扣次与报名结算关联原子完成；失败不能出现“次数少了但报名没关联”。
- 同一期次三天签到不触发三次扣次。具体一次活动消耗多少次、何时消耗，由第 13 节业务确认后配置。
- 已使用流水更正采用关联原记录的冲正/更正，保留原因，不删除旧流水；取消报名不默认自动返次。
- 手机端主要消费与查询；开户、初始余额核验、赠送、调整和争议处理放电脑后台。
- 卡次使用不制造现金收款事实；轻友端显示“卡次已登记”等明确结算结果，不能显示为微信支付成功。

首期不做跨人转让、多个卡组合抵扣、卡次与现金混合支付；如真实业务必须使用，需在灰度前确认是否扩大范围，不能临场猜测处理。

### W08 快速记录与附件

目标：将一次沟通及时关联到轻友，其他有权限工作人员能够接续。

最小字段：轻友必填；期次可选；渠道（微信/电话/语音/线下/其他）；发生时间默认当前；简短摘要或至少一个附件；可选后续动作。作者自动记录。

- 图片支持拍照或选取，语音/文件支持受控上传；首期保留原材料，不做转写和摘要。
- 先明确关联轻友，再上传；附件继承记录访问范围，服务端下载仍检查权限，不能使用永久公开链接作为内部资料访问方式。
- 上传过程显示进度和失败重试；部分附件失败时明确哪些尚未保存，可选择仅保存成功部分，不能声称全部成功。
- 文本、图片、语音、文件均须有真实保存/读取验收；具体格式和大小上限在实现前按存储及小程序能力确定，并在界面显示。
- 照片含多名轻友时不自动关联所有人；人员关联由工作人员核实。敏感资料没有相应授权时不能随意上传扩散。
- 修改保留历史；记录纠错或附件撤回保留必要操作审计，原材料保留/删除按授权与留存规则处理，不以“审计”为由无限保留敏感文件。
- 后续动作有填写时，要求负责人和计划日期；沟通保存与任务建立结果明确，失败不漏掉跟进事项，也不重复建记录。

### W09 回访列表与详情

目标：每件待办有负责人、日期和处理结果。

- 状态：待处理、已完成、已关闭；逾期由日期计算，不需要额外状态。
- 来源：快速记录生成或档案手动创建；自动第 3 天回访不进入首期。
- 字段：轻友、可选期次、动作说明、负责人、计划日期、来源记录。
- 完成需简短结果和实际完成时间；无需继续时可关闭并写原因；改负责人或日期留变更记录。
- 负责人必须为可用工作人员账号；账号停用时待办需移交，不删除。
- 默认不发送微信消息、短信或订阅提醒。工作人员主动打开工作台查看，避免将任务登记误称自动触达。

### W10 工作身份与最近操作

目标：工作人员明确当前身份和权限，能找到自己的最近处理记录。

- 显示工作称呼、账号状态、角色和允许动作的简明说明。
- 最近操作列出自己提交的报名、付款、签到、卡次、沟通及任务，点击进入有权查看的详情。
- “返回轻友端”只退出工作界面；“退出登录”清除当前设备会话和敏感页面缓存。
- 不提供自行提升权限、前端角色切换模拟或填写口令成为管理员。

## 6. 权限与工作账号

### 6.1 开通和撤销

小程序真实登录 → 后台管理员核实并选择该身份 → 关联现有内部账号 → 分配权限 → 小程序刷新身份后显示入口。

不得仅凭昵称、手机号相同自动绑定工作人员。账号绑定标识由系统内部匹配，不要求工作人员在微信聊天中发送会话密钥等凭据。一项小程序身份与内部账号的有效绑定必须唯一且可撤销，所有授权变更留记录。

普通用户直接打开工作台路径时，服务端返回无权限，不返回内部数据。每次敏感读写检查最新授权；停用账号或撤销绑定后，旧会话也无法继续内部访问，前端清理已加载的内部资料。仅隐藏入口不算完成权限控制。

### 6.2 最小动作权限建议

沿用已有内部账号体系，不新建重复角色平台；以下为建议动作矩阵，实际开通前确认人员名单。

| 动作 | 管理员 | 运营 | 导游 | 财务 |
| --- | --- | --- | --- | --- |
| 查看全部期次及必要名单 | 是 | 是 | 是 | 是 |
| 查看基础档案 | 是 | 是 | 按必要字段 | 按必要字段 |
| 修改资料、人工报名、确认报名 | 是 | 是 | 默认否 | 默认否 |
| 登记到场 | 是 | 是 | 是 | 默认否 |
| 查看付款金额 | 是 | 是 | 默认否 | 是 |
| 登记收款 | 是 | 单独授予 | 默认否 | 是 |
| 查看卡次、登记使用 | 是 | 单独授予 | 默认否 | 按职责授予 |
| 查看沟通附件 | 按资料授权 | 按资料授权 | 按资料授权 | 默认否 |
| 新增观察/沟通和本人回访 | 是 | 是 | 按职责授予 | 默认否 |
| 财务/卡次更正、改期结算 | 是 | 默认否 | 否 | 单独授予 |
| 账号授权、合并、批量导出 | 电脑后台 | 否 | 否 | 否 |

管理员不因系统角色自动获得所有私人感受的访问权。资料访问还需满足用途、本人授权与字段范围；内部沟通与轻友本人记录分别管理。内部记录不能被代报名人、邀请人或普通轻友读取。

## 7. 关键数据和状态规则

| 对象 | 核心关联与约束 |
| --- | --- |
| 轻友主档案 | 每位轻友一个主体；重复和冲突人工核实，不按同名/同手机自动合并 |
| 工作身份 | 微信登录身份关联既有内部账号；停用、授权和解绑可追溯 |
| 期次 | session_number 必填、正整数、唯一；连续三天属于同一期次 |
| 报名与订单 | 分清实际参与人和购买人；报名确认、到场、付款/卡次结算独立 |
| 参与 | 日到场事实与整期完成不同；不因缺一次签到直接改写历史参与资格 |
| 收款 | 记录真实线下金额、方式、时间与操作人；更正保留历史 |
| 卡次账户与流水 | 归属本人，流水可核算余额；使用关联报名及期次；不能只修改余额数字 |
| 沟通与附件 | 明确轻友、可选期次、来源、作者、时间、范围和修改历史 |
| 回访 | 关联轻友、负责人和日期；完成与关闭均有结果 |
| 授权 | 保存用途、范围、版本及生效/撤销事实，不能只是本机开关 |
| 审计 | 身份绑定、敏感查看、修改、付款、更正、扣次、导出与合并保留操作记录 |

业务返回成功后再更新显示；查询失败保留明确错误状态，不能回退 Demo 假数据。敏感内容不长期存入本机本地存储；网络失败时不假装离线提交成功。

## 8. 电脑后台与轻友端配套

| 产品面 | 必须配套 | 不在移动端重复建设 |
| --- | --- | --- |
| 电脑后台 | 工作身份绑定与权限；卡次开户、核验和更正；改期结算；导入预览/冲突；必要审计 | 批量数据处理、复杂期次配置 |
| 轻友端 | 本人报名/付款或卡次结算、活动、卡次余额/使用记录、真实隐私授权 | 内部沟通、主观观察和其他轻友资料 |
| 服务端 | 统一数据、动作权限、附件受控读取、重复提交防护、业务事务 | 不能由小程序本地状态决定权限或余额 |

历史导入首期至少支持一份确定模板和受控批次：上传预览→新增/重复/冲突/失败分类→人工确认→入库结果与来源追溯。未核实卡次不能伪装成可用余额。历史照片逐步手工关联，不承诺全量自动归档。

## 9. 异常与边界验收

| 异常 | 必须表现 |
| --- | --- |
| 权限被撤销或账号停用 | 下次请求拒绝内部数据；退出内部页面并清理缓存 |
| 两个同名轻友/共用手机号 | 展示候选区别，不自动合并，不自动绑定微信 |
| 网络超时但服务端可能已提交 | 先查询提交结果，安全重试，不重复报名、收款或扣次 |
| 两人同时处理同一付款/扣次 | 至多产生一次有效业务结果；另一端刷新真实状态 |
| 卡次余额不足/历史未核实 | 阻止使用并说明原因，不能临时填负数通过 |
| 活动满员/关闭或已结束 | 按服务端规则阻止或进入已确认的人工处理流程 |
| 已有付款/扣次后取消或改期 | 明确待处理结算，不自动退款返次，不丢原记录 |
| 附件上传失败或无权读取 | 明确失败和重试/无权限，不能展示他人链接 |
| 工作人员离职有未完成任务 | 管理员可移交，保留原负责人历史 |
| 用户撤回资料授权 | 后续访问按新范围执行，已有资料按留存规则处理 |

## 10. 界面与文案约束

- 沿用轻生活现有视觉规范，优先可读和可操作；不启动新一轮品牌 UI 重做。
- 一个页面突出一个主要动作；数值输入有足够宽度，金额、单位和对象一起展示。
- 日期默认选日期，发生时间需要精确记录时才展示时间；后台统一日期边界。
- 状态使用清楚文案：“报名已确认”“收款已登记”“卡次已使用”“待核实”；不用单一“成功”掩盖业务区别。
- 列表柔和刷新，提交中禁重复操作；失败保留可恢复的非敏感输入，工作身份失效时清除内部资料。
- 内部页面不提供外部分享按钮，不把档案内容放入分享卡片；必要联系动作按权限提供。

| 阶段 | 产出 | 完成条件 |
| --- | --- | --- |

| B 身份与核心移动入口 | 授权绑定、W01/W02/W04/W10、基础档案 | 普通用户不可进入；授权人员手机查人看名单 |
| C 运营事务 | W05/W06/W07、档案事实、轻友端余额与结算同步 | 报名、付款、扣次、重复提交及更正验收 |
| D 服务记录 | W08/W09、附件、回访和时间线、真实授权 | 两名授权工作人员可接续记录与任务 |
| E 灰度交付 | 首批导入、冲突样例、实机权限和恢复验证、手册 | 第 12 节通过，遗留问题逐项列明 |

代码组织建议：现有原生小程序增加独立工作人员分包；现有后台复用账号和业务服务，补工作人员接口；数据库升级在已有卡次、沟通、附件、授权等结构上增量实现。本文不预设具体 URL、字段迁移或接口已存在，开发前按实际服务核对，避免把建表资产当成已完成接口。

优先复用已验证的期次、报名、收款与签到规则，不复制一套仅供手机使用的业务逻辑。每阶段可单独演示，但 B 阶段完成不能宣称完整 MVP 交付。

## 12. MVP 验收清单

| 编号 | 验收场景 | 通过条件 |
| --- | --- | --- |
| A01 | 普通轻友与授权工作人员分别登录 | 普通人看不到入口，直接路径/API 均无权；工作人员可进入 |
| A02 | 开通、解绑、停用工作账号 | 最新权限生效，旧会话无法越权，日志可追溯 |
| A03 | 新轻友小程序报名→移动处理收款→本人查询 | 同一档案/报名，金额与状态一致，时间线有处理人和事实 |
| A04 | 有多期历史与卡次的老轻友现场参加 | 找到历史与余额→报名→核实扣次→本人余额同步→档案流水一致 |
| A05 | 沟通与照片、语音、文件 | 关联正确轻友，另一授权人员可查看，无权限者不可读 |
| A06 | 沟通生成回访→改日期/负责人→完成 | 工作台分组准确，结果进入时间线，变更可查 |
| A07 | 多人报名、新老资格、代报名 | 按参与人资格计价，购买人不获得同行者私人记录访问权 |
| A08 | 双击、网络重试、并发收款/扣次 | 不重复产生有效交易或使用，不出现负余额和部分关联 |
| A09 | 报名取消/改期与更正 | 保留原期次和账务关联；待处理与已完成明确，不虚构退款 |
| A10 | 同名、共用手机及历史冲突 | 不自动合并，受控人工核实；导入结果有分类和来源 |
| A11 | 权限及隐私 | 导游/运营/财务动作按批准矩阵；本人感受默认不向内部公开；授权跨设备一致 |
| A12 | 备份恢复与手机彩排 | 隔离环境完成恢复验证并核对关键事实；实际工作人员达到第 2 节效率目标 |

采用一个新轻友、一个有多期历史和卡次的老轻友真实或完整脱敏样例，配合不同角色设备测试。不能用固定验证码、本地模拟余额、Mock API 或单纯 HTTP 200 代替验收。

交付物：测试入口及账号开通说明、工作人员简明操作手册、权限矩阵、数据变更说明、部署与恢复记录、验收结果、已知问题。涉及正式发布另按发布流程执行，不把内部灰度等同正式上线。

## 13. 开发前及灰度前必须明确的决策

| 决策 | 当前事实/缺失 | 阻断范围 |
| --- | --- | --- |
| 实际人员与动作权限 | 有角色方向，未逐人确认；收款/扣次/更正应明确授权 | 真实工作账号开通 |
| 卡次规则 | 卡类型、一次活动消耗次数、扣减时点、有效期、取消返次、旧余额来源待确认 | 卡次实现与老轻友验收 |
| 混合结算/部分收款 | 首期建议不扩展；现行业务是否必须使用需确认 | 金额与卡次结算规则 |
| 已结算改期 | 差价、原付款承接、卡次冲正与重新使用口径待确认 | 已结算报名改期 |
| 人工补录限制 | 是否允许窗口外补录、由谁操作、满员如何处理待确认 | 人工报名例外 |
| 整期完成口径 | 现有老轻友资格用已确认报名且期次完成；实际参与核验与历史缺席处理需运营确认 | 防止将未实际参与误认成老轻友 |
| 附件授权与留存 | 谁有权看哪些沟通、照片、语音；撤回与删除处理待确认 | 敏感附件真实使用 |
| 首批导入与灰度样例 | 轻友、期次、卡次与身份线索需明确范围和核实人 | 数据初始化和最终验收 |

以上缺失不阻止页面结构和通用权限设计，但相关业务不能靠假定规则上线。建议优先确认卡次和人员授权，再冻结开发范围。
