# 轻生活轻友统一档案｜产品设计 V1.1

> 文档日期：2026 年 8 月 27 日  
> 产品定位：以后台为主、移动采集为重点、轻友前端为补充的统一档案与关系服务系统  
> 设计依据：2026 年 8 月 26 日需求沟通记录、既有轻生活产品/数据库文档、轻生活打卡小程序审计与品牌小程序升维方案、现有 H5 测试 Demo 及过往轻生活数字化讨论  
> 术语：本文统一使用“轻友”，指轻生活的用户、参与者及长期关系对象。

---

## 版本更新记录

### V1.1｜2026 年 8 月 27 日

本版本只修订端口定位与小程序衔接方案，不改变轻友统一档案的核心对象、轻输入原则和 AI 治理规则：

- 明确现有轻友端 H5 仅用于需求、流程和视觉验证，不作为正式上线端。
- 正式轻友端继续使用微信小程序渠道，按“轻生活体验与习惯陪伴小程序”方向升级。
- “继续使用原有小程序”指保留微信小程序载体、项目配置和可迁移资产，不代表在旧文章/社区骨架上继续堆功能。
- 新版小程序采用新产品骨架、新业务 API 和新数据模型；旧内容、OpenID 等经规则迁移或映射。
- 内部完整工作系统仍以 Web 后台和响应式移动 H5 为主；需要微信原生能力时，在正式品牌小程序中增加授权角色可见的工作入口，原则上不再建设第二个重复的小程序。

V1.0 保持不变，作为修订前基线留存。

## 0. 一页结论

### 0.1 产品不是传统 CRM

轻友统一档案不应被做成一套字段很多、依赖工作人员持续填表的 CRM，而应是一套“轻记录、强关联、可追溯”的关系服务系统：

```text
快速找到轻友
→ 用最自然的方式留下原始信息
→ ASR/LLM 自动整理成待确认草稿
→ 工作人员一眼检查并确认
→ 信息进入轻友时间线
→ 自动形成下一步待办
```

系统的价值不在于“录入了多少字段”，而在于：

- 重要信息不再只存在于个人脑中、微信、Excel 和照片文件夹里。
- 工作人员减少重复输入和查找，把时间用于与轻友交流。
- 同一轻友的参与、交易、卡次、沟通、照片和后续动作可连续追溯。
- 轻友可以查看自己的必要记录、授权和服务状态。
- AI 只负责减轻整理负担，不替代事实、不替代人工判断。

### 0.2 推荐产品形态

推荐采用三层形态，共用一套业务数据：

1. **Web 管理后台：主系统。**用于完整档案、批量管理、数据治理、权限和审计。
2. **内部移动采集端：高频入口。**首期用响应式 H5 快速交付；后续如需微信原生录音、拍照和身份能力，在正式品牌小程序中增加授权工作人员入口。
3. **轻友端：正式上线使用升级版微信小程序。**现有 H5 只作为测试 Demo；新版小程序承接活动、报名、体验、习惯陪伴和本人可见档案信息。

### 0.3 H5 与小程序的最终建议

不是二选一，而是分阶段使用：

- **后台与内部工作：响应式 Web/H5。**一个后台同时覆盖电脑和手机，便于快速跑通统一档案和移动记录闭环。
- **正式轻友端：升级版微信小程序。**沿用原有微信小程序渠道，但按新品牌旅程重建信息架构、业务 API 和核心数据模型。
- **现有 H5：仅作测试验证。**用于验证需求、页面、文案和流程，不作为正式轻友端，也不把其本地演示数据视为正式业务事实。
- **内部微信入口：复用正式品牌小程序。**当带领人/工作人员确有高频微信场景时，以角色授权方式开放快捷工作入口，不重复建设一套独立小程序。

### 0.4 AI 接入结论

建议首期支持一个 ASR 服务和一个 LLM 服务，但必须满足：

- API Key 只保存在服务端，绝不进入 H5、小程序代码或接口响应。
- 录音先形成原始材料，AI 结果只形成“待确认草稿”。
- 工作人员确认后才进入正式档案。
- ASR/LLM 故障时，原始记录仍能保存，不能阻断工作。
- 发送给外部模型的数据遵循最小必要原则，手机号等直接标识先脱敏。
- 医疗健康信息、未成年人信息等敏感个人信息单独授权、严格控制访问。

## 1. 产品背景与问题定义

### 1.1 当前信息分布

轻友相关信息主要分散在：

- 大海、公主、桃子、彩虹等工作人员的个人记忆。
- 微信一对一聊天、群聊、语音和截图。
- 电话和线下沟通。
- 历史 Excel 名单、付款和卡次表。
- 按期次保存的照片文件夹。
- 微店订单及其他收款记录。
- 现有 H5 测试 Demo 的本地演示数据，以及旧打卡小程序中的历史用户、文章、动态和身份线索。

这些信息虽然存在，但没有形成团队可持续使用的轻友资产。

### 1.2 核心问题

#### 问题一：找不到

- 不知道一位轻友第一次参加哪一期。
- 不知道照片在哪个期次文件夹。
- 不知道历史上谁和这位轻友沟通过什么。
- 临时到场时无法在手机上确认剩余卡次。

#### 问题二：记不下

- 沟通发生在微信、电话或线下，系统不在当下场景里。
- 交流后再要求填写完整表单，工作人员容易放弃。
- 批量复制聊天记录会带来大量无关信息和隐私风险。

#### 问题三：信息无法共享

- 不同工作人员掌握的是同一轻友的不同片段。
- 信息没有来源、时间和记录人，后续无法判断可信度。
- 主观判断可能被其他人误当成客观事实。

#### 问题四：没有下一步

- 即使留下了记录，也未必形成明确的回访任务。
- 重要事项仍依赖工作人员自己记住。
- 无法判断哪些轻友今天真正需要联系。

### 1.3 产品机会

本产品要将“档案”从被动存储变成服务工作台：

```text
关系事实沉淀
→ 服务上下文共享
→ 下一步动作明确
→ 工作人员时间被释放
→ 轻友体验连续
```

## 2. 产品目标与非目标

### 2.1 产品目标

#### G1：统一

每位轻友只有一个主档案，报名、参与、付款、卡次、推荐、沟通、附件和回访都关联到同一个主体。

#### G2：轻盈

工作人员可以用语音、短文字、拍照或业务动作自动留档，而不是重复填写长表单。

#### G3：可信

所有信息保留来源、发生时间、记录时间、记录人、可见范围和修改历史。

#### G4：协作

授权工作人员能够在同一上下文中继续服务，而不是重新询问轻友或依赖转述。

#### G5：可行动

重要记录能快速转为回访任务，工作台能显示今天真正需要处理的事。

#### G6：面向未来

为 21 天陪伴、内容推荐、AI 辅助搜索和经营分析建立干净的数据基础。

### 2.2 首期非目标

- 不做医疗诊断、心理判断或疗效评价。
- 不自动判断轻友价值、流失风险或服务优先级。
- 不把自由文本自动变成永久标签。
- 不自动读取工作人员微信聊天数据库。
- 不做完整企微 SCRM 或营销自动化平台。
- 不做复杂商城、库存、物流和财务系统。
- 不做全量历史照片人脸识别。
- 不要求一次性清洗完所有历史数据。
- 不让 AI 自动决定联系谁、说什么或采取何种健康干预。

## 3. 用户、角色与权限

### 3.1 主要角色

| 角色 | 主要任务 | 默认数据范围 |
|---|---|---|
| 系统管理员 | 账号、角色、权限、配置、审计、数据恢复 | 全局，但敏感数据查看仍需审计 |
| 运营工作人员 | 轻友档案、报名、付款、卡次、沟通、回访 | 按授权的全部或部分轻友 |
| 带领人 | 查看本期必要信息、记录场次事实和建议回访 | 仅本人负责期次及授权时间窗 |
| 财务/收款 | 确认交易、查看对账必要信息 | 交易字段，不默认查看敏感沟通 |
| 数据维护人员 | 历史导入、冲突处理、合并建议 | 脱敏资料优先，敏感信息最小化 |
| 轻友本人 | 查看/修改本人必要资料、活动、卡次、授权 | 仅本人可见内容 |

### 3.2 权限原则

- 页面权限、操作权限和字段权限分开控制。
- “入口隐藏”不等于权限控制，服务端必须再次鉴权。
- 带领人按具体期次授权，而不是获得全部轻友档案。
- 手机号、医疗健康信息、沟通原文、照片和语音默认限制访问。
- 查看敏感详情、导出、合并、删除和修改关键业务事实进入审计日志。
- 普通工作人员不直接接触 AI API Key。

## 4. 产品整体架构

```text
┌──────────────────────────────────────────────────────────┐
│                   统一业务服务层                          │
│ 身份认证｜档案｜期次｜报名｜参与｜交易｜卡次｜沟通｜回访 │
│ 文件服务｜AI编排｜权限｜审计｜导入｜搜索                  │
└───────────────┬───────────────────────┬──────────────────┘
                │                       │
     ┌──────────▼──────────┐  ┌─────────▼────────────┐
     │ Web 管理后台         │  │ 正式品牌微信小程序   │
     │ 电脑完整操作         │  │ 轻友体验与习惯陪伴   │
     │ 手机响应式快速操作   │  │ 本人档案/授权/记录   │
     └─────────────────────┘  │ 授权角色工作入口     │
                              └──────────────────────┘

H5 测试 Demo：仅连接测试环境，用于需求和交互验证，不作为正式端
外部能力：ASR｜LLM｜对象存储｜短信/微信服务通知
```

### 4.1 架构原则

1. Web 后台、移动 H5 工作入口和正式品牌小程序使用同一套新业务 API 和同一套业务事实。
2. Web 后台是完整能力中心；移动端只保留现场高频动作。
3. AI 服务通过后端编排层调用，前端不直接访问外部模型。
4. 原始材料、AI 草稿和人工确认记录分层保存。
5. 档案查询优先使用结构化事实；AI 搜索只是辅助入口。
6. 旧小程序和 H5 Demo 只作为迁移源或产品参考，不得与新系统同时写入核心业务事实。

1. 找到轻友。
2. 看关键上下文。
3. 留下一条记录。
4. 完成一个业务动作。
5. 安排下一步。

## 6. 轻友档案详细设计

### 6.1 档案页结构

#### 顶部身份区

- 常用称呼/小名作为主标题。
- 真实姓名作为身份核对字段。
- 手机号默认脱敏。
- 头像或确认过的个人照。
- 城市、微信号、账号绑定状态。
- 新轻友/老轻友、首次参加期次、最近参加期次。
- 快速操作：语音记录、文字记录、上传附件、新建回访。

#### 关键摘要卡

首屏只显示高频事实：

- 最近一次参加。
- 当前报名。
- 当前卡次余额。
- 最近一次沟通。
- 下一个待办。
- 需要注意的服务信息。

不在首屏展示：

- 复杂画像标签。
- AI 生成的人格描述。
- 未经确认的健康结论。
- 不透明的价值或风险评分。

### 6.2 档案页签

#### A. 时间线

统一展示所有关键事件：

- 建档和资料变更。
- 报名、付款、改期、参与和完成。
- 卡次购买、消耗和更正。
- 沟通记录和回访结果。
- 照片、语音和文件。
- 授权变化。

支持按类型筛选，但默认按时间阅读，避免信息被拆散。

#### B. 活动与期次

- 首次参加期次。
- 历次报名与实际参与。
- 取消、改期、缺席等状态。
- 本期邀请人和回归原因。
- 轻友在每一期的自述及服务记录。

#### C. 交易与卡次

- 实际付款时间、金额、方式、归属期次和确认人。
- 卡类型、总次数、已使用、剩余次数和有效期。
- 卡次流水逐笔关联具体期次。
- 更正必须填写原因，原记录不可消失。

#### D. 沟通与跟进

- 微信、电话、语音、线下等渠道。
- 原始记录、人工确认摘要、涉及主题。
- 后续动作、负责人和计划日期。
- 待跟进、处理中、已完成、已关闭。

#### E. 照片与附件

- 个人照、合照、截图、语音和文档。
- 关联轻友、期次、发生时间和上传人。
- 支持按期次、类型、时间筛选。
- 同一附件可关联多个轻友，但每个关联都需人工确认。

#### F. 授权与数据权利

- 服务必要信息授权。
- 运营联系授权。
- 敏感信息处理授权。
- ASR/LLM 辅助处理授权。
- 用户查看、更正、撤回和删除申请。

### 6.3 档案摘要的生成规则

档案首页摘要只由两类内容组成：

1. 可计算的客观事实，如参加次数、最近期次、卡次余额。
2. 人工确认的沟通摘要和待办。

AI 可以建议摘要，但不能直接覆盖人工确认结果。

## 7. “轻输入”交互设计

### 7.1 总原则

工作人员完成一次输入时，系统尽量只要求一个主动动作：

- 从轻友档案进入时，只需说或写内容。
- 从全局入口进入时，只需先选择轻友，再说或写内容。
- 时间、操作人、入口、设备、来源和当前期次尽可能自动带入。

### 7.2 全局快速记录入口

后台和移动端均提供固定的“＋记录”入口：

```text
语音速记｜短文字｜拍照/截图｜付款｜卡次｜回访
```

系统根据入口自动选择最小表单，而不是先让用户选择十几个分类。

### 7.3 语音速记

#### 推荐交互

```text
点击“语音速记”
→ 最近轻友列表/搜索轻友
→ 点击开始，说完点击结束
→ 立即显示“已保存原始录音”
→ 后台完成 ASR 和 LLM 整理
→ 展示一张待确认卡片
→ 工作人员修改或一键确认
```

#### 待确认卡片只显示

- 一句话摘要。
- 识别到的客观事实。
- 轻友自述。
- 工作人员观察。
- 建议下一步及日期。
- 敏感信息提醒。
- 原文展开入口。

避免把工作人员重新带回长表单。

### 7.4 短文字

- 单输入框直接保存。
- 支持自然语言，例如：“今天和小树微信聊了，她准备参加 503 期，周五再确认。”
- LLM 可解析期次和待办，但保存前必须确认。
- 按回车或点击保存后不弹出额外必填表单。

### 7.5 拍照与截图

适合：

- 轻友个人照。
- 期次合照。
- 微信重要聊天截图。
- 付款截图或纸质记录。

最小流程：

```text
拍照/选择图片
→ 选择轻友或期次
→ 可选说一句说明
→ 保存
```

OCR/视觉模型可以建议图片类型、文字摘要和关联对象，但不能自动认定照片中的人物身份。

### 7.6 业务动作自动留档

下列信息不应要求工作人员再写一遍：

- 报名自动形成报名事件。
- 付款确认自动形成交易事件。
- 改期自动保留原期次和新期次关系。
- 卡次消耗自动形成流水。
- 回访任务完成自动形成跟进结果。
- 轻友本人提交的记录自动注明“本人自述”。

### 7.7 草稿和容错

- 录音完成即先保存原始文件，再调用 ASR。
- 网络中断时保留本地草稿并提示稍后重试。
- AI 失败时仍能播放原音、手工补充并保存。
- 关闭页面前自动保存未提交草稿。
- 同一素材重复上传时提示疑似重复，不武断删除。

## 8. ASR 与 LLM 产品设计

### 8.1 AI 的职责边界

AI 只负责：

- 语音转文字。
- 长文本压缩为短摘要。
- 把事实、自述、观察和判断分区。
- 提取可能的期次、日期和下一步。
- 提示敏感信息和待确认歧义。
- 建议内容标签，供人工选择。

AI 不负责：

- 判断轻友疾病、心理状态或疗效。
- 自动决定是否回访或如何干预。
- 自动合并两个疑似同一人的档案。
- 将聊天原文无审核地写入永久档案。
- 自动对轻友评分、分层或贴人格标签。

### 8.2 处理链路

```text
原始输入
  ↓
安全上传与病毒/格式检查
  ↓
ASR / OCR
  ↓
去除手机号等直接标识或使用占位符
  ↓
LLM 结构化整理
  ↓
规则校验与字段置信度
  ↓
工作人员待确认卡片
  ↓
人工确认
  ↓
正式档案 + 回访任务 + 审计记录
```

### 8.3 LLM 输出结构

模型必须返回结构化 JSON，不允许只返回一段不可控文字。建议结构：

```json
{
  "summary": "一句话摘要",
  "facts": [
    { "text": "客观发生的事实", "evidence": "原文片段", "confidence": 0.91 }
  ],
  "customer_statements": [
    { "text": "轻友本人表达", "evidence": "原文片段", "confidence": 0.88 }
  ],
  "staff_observations": [],
  "staff_judgements": [],
  "session_number_candidate": 503,
  "follow_up": {
    "needed": true,
    "suggested_date": "2026-08-29",
    "action": "确认是否参加第503期"
  },
  "sensitive_flags": ["health"],
  "unresolved_questions": []
}
```

模型输出中的 `confidence` 只代表抽取置信度，不代表事实真实性。

### 8.4 AI 运行状态

```text
已保存原始材料
→ 等待转写
→ 转写中
→ 等待整理
→ 整理中
→ 待人工确认
→ 已确认入档

异常分支：转写失败 / 整理失败 / 人工退回 / 已放弃
```

任何失败状态都应允许重试或手工完成。

### 8.5 API Key 与服务配置

#### 强制规则

- API Key 只保存在服务端环境变量或密钥管理服务中。
- 前端、小程序、日志、数据库导出和错误提示不返回完整 Key。
- 每个供应商使用独立 Key，支持轮换和立即停用。
- 测试环境与正式环境使用不同 Key。
- 按能力拆分权限：ASR Key 只调用 ASR，LLM Key 只调用指定模型。
- 配置用 `secret_ref` 引用密钥，不在业务表中保存明文。

#### AI 服务配置字段

| 字段 | 说明 |
|---|---|
| `provider` | 服务商 |
| `capability` | ASR / LLM / OCR / embedding |
| `endpoint` | 服务端地址 |
| `model` | 模型或识别版本 |
| `secret_ref` | 密钥引用 |
| `region` | 数据处理地区 |
| `retention_policy` | 服务商数据保留规则 |
| `training_opt_out` | 是否明确不用于训练 |
| `timeout_ms` | 超时配置 |
| `daily_budget` | 每日费用上限 |
| `enabled` | 是否启用 |

### 8.6 供应商选择标准

ASR 优先评估：

- 普通话及轻生活常用词识别效果。
- 较长语音、停顿、口语和多人谈话能力。
- 标点、时间数字和自定义热词。
- 音频保存政策和处理区域。
- 延迟、失败重试和按时长计费。

LLM 优先评估：

- 稳定输出指定 JSON Schema。
- 中文口语摘要质量。
- 企业数据是否默认用于训练。
- 数据处理地区和跨境要求。
- 请求日志、删除和审计能力。
- 成本、速率限制和服务可用性。

产品不应绑定单一模型。首期只需要实现一个供应商，但后端保留统一适配接口。

### 8.7 数据最小化

每次 AI 调用只发送完成当前任务所需内容：

- ASR 只接收本次音频。
- LLM 只接收本次转写和必要上下文，不发送整张轻友档案。
- 姓名、手机号、地址等直接标识优先替换为占位符。
- 需要识别期次时只提供当前开放期次列表，不提供无关历史。
- AI 结果保存输入范围、模型、提示词版本、输出和人工采纳状态。

### 8.8 建议保留周期

以下为产品建议，正式上线前需由业务和合规共同确认：

| 数据 | 建议策略 |
|---|---|
| 未完成上传草稿 | 24 小时后清理 |
| 原始音频 | 人工确认后默认保留 7 天，可按用途设为立即删除/7天/30天 |
| ASR 原始转写 | 与确认记录关联，支持更正和追溯 |
| LLM 草稿 | 保存模型和版本，用于审计；不作为用户事实 |
| 人工确认记录 | 按业务必要期限保存 |
| 已放弃素材 | 短期清理，不无限期留存 |

## 9. 核心数据对象

### 9.1 沿用对象

- `Customer`：唯一轻友主体。
- `Session`：唯一明确业务期次。
- `Registration`：报名事实。
- `Participation`：实际参与事实。
- `Transaction`：真实交易事实。
- `ConsentRecord`：授权记录。
- `AuditLog`：关键操作审计。
- `ImportBatch`：历史导入批次。

### 9.2 新增或强化对象

#### CustomerIdentifier

保存身份线索：

- 当前及历史手机号。
- 真实姓名、小名、历史称呼。
- 微信 OpenID/UnionID 等外部身份。
- 来源、有效期、是否已验证。

不得仅凭姓名自动合并轻友。

#### Interaction

一次沟通或服务接触的核心记录：

| 字段 | 说明 |
|---|---|
| `customer_id` | 实际轻友 |
| `session_id` | 可选关联期次 |
| `occurred_at` | 实际发生时间 |
| `recorded_at` | 系统记录时间 |
| `operator_id` | 记录人 |
| `channel` | 微信/电话/线下/语音/其他 |
| `input_type` | text/audio/image/file/system_event |
| `summary` | 人工确认摘要 |
| `visibility_scope` | 内部范围/带领人范围/用户可见 |
| `sensitivity_level` | 普通/敏感/高度敏感 |
| `confirmation_status` | 草稿/待确认/已确认 |

#### InteractionContent

将内容分层保存：

- 原始文字或文件引用。
- 轻友自述。
- 客观事实。
- 工作人员观察。
- 工作人员判断。
- AI 建议。

不同类型必须显式标识，避免被合并成一段无法分辨来源的“备注”。

#### Attachment

- 文件地址、类型、大小和哈希。
- 上传人、上传时间和原始文件名。
- 关联轻友、期次和 Interaction。
- 可见范围、敏感等级和保留策略。
- 病毒/格式检查状态。

#### Transcript

- 原始音频引用。
- ASR 服务商、模型和语言。
- 转写原文、分段和时间戳。
- 人工修改版本。
- 状态和错误原因。

#### AIProcessingRun

- 任务目的。
- 输入对象和最小上下文范围。
- 服务商、模型、提示词/Schema 版本。
- 原始输出和解析结果。
- 费用、耗时和错误。
- 人工采纳、修改或拒绝结果。

#### FollowUpTask

- 轻友、关联期次和来源记录。
- 任务内容、负责人和计划日期。
- 优先级只允许人工或明确规则设置。
- 待处理、处理中、已完成、已关闭。
- 完成结果自动回写时间线。

#### PassAccount / PassLedger

- 卡类型、总次数、有效期。
- 购买、使用、调整和作废流水。
- 使用记录必须关联具体期次。
- 余额通过流水计算，不手工覆盖。

#### MergeCandidate

- 疑似重复的两个轻友。
- 匹配证据和冲突字段。
- 建议但不自动执行。
- 人工确认人、时间和合并结果。

### 9.3 所有记录的通用字段

所有业务对象至少保留：

- 唯一 ID。
- 实际发生时间和系统记录时间。
- 来源类型和来源主体。
- 实际数据主体。
- 创建人和最后修改人。
- 可见范围和敏感等级。
- 当前状态和历史版本。
- 删除/失效状态，不直接物理消失。

## 10. 搜索与查找设计

### 10.1 直接搜索

支持：

- 姓名。
- 小名/历史称呼。
- 当前及历史手机号。
- 明确期号。
- 最近沟通关键词。

手机号搜索结果默认脱敏；只有具备权限的人员才能查看完整号码。

### 10.2 档案内搜索

- 按时间范围。
- 按期次。
- 按记录类型。
- 按工作人员。
- 按附件类型。

### 10.3 AI 问档案

作为 P2 能力，仅回答有证据的问题，例如：

- “这位轻友最近一次参加是哪一期？”
- “关于卡次，最近一次确认记录是什么？”
- “最近三个月有哪些明确的待办？”

回答必须附来源记录和时间，不能只返回无证据结论。

## 11. Web/H5 与小程序分工

### 11.1 能力对比

| 维度 | 响应式 Web/H5 | 微信小程序 |
|---|---|---|
| 开发与发布速度 | 快，无需每次走小程序审核 | 相对慢，需要版本提交和审核 |
| 电脑端完整后台 | 最适合 | 不适合复杂后台和批量操作 |
| 手机端表单 | 可用，容易与后台共享代码 | 移动体验更统一 |
| 微信内进入 | 链接可直接打开，但身份仍需系统登录 | 入口更稳定，可结合微信登录 |
| 录音 | 可通过 Web API 实现，但需 HTTPS、权限和设备兼容测试 | 原生 `RecorderManager` 路径更稳定 |
| 拍照/相册 | 可用文件选择与相机能力，设备差异较大 | 微信内能力和交互更统一 |
| 服务提醒 | 主要依赖短信、公众号或页面内待办 | 可使用用户主动订阅后的服务通知 |
| 迭代频率 | 高，发布后立即生效 | 受审核和版本发布节奏影响 |
| 多端复用 | 电脑、平板、手机都可使用 | 主要在微信移动端 |
| 内部权限 | 依赖账号、MFA 和服务端鉴权 | 微信身份更方便，但仍必须服务端鉴权 |
| 现有资产 | H5 Demo 可验证需求，但不是正式产品资产 | 已有微信小程序渠道、历史身份和内容资产；新业务骨架仍需重建 |
| 适合场景 | 完整后台、快速迭代、跨设备操作 | 高频语音、拍照、微信身份和消息触达 |

H5 录音依赖 `getUserMedia`/`MediaRecorder`，必须在 HTTPS 安全上下文中请求用户授权；不同浏览器和微信 WebView 仍需真机验证。[W3C MediaStream Recording](https://www.w3.org/TR/mediastream-recording/)、[MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)

微信小程序提供统一的录音管理器，并能获得临时录音文件后上传；微信登录也有明确的临时凭证换取服务端登录态流程。[腾讯云录音能力说明](https://cloud.tencent.com/document/product/1301/109326)、[腾讯云微信小程序登录说明](https://cloud.tencent.com/document/product/1441/68677)

### 11.2 对轻友端的建议

**正式上线使用升级版微信小程序，H5 只保留为测试 Demo。**

这里的“升级原有小程序”需要明确为：

```text
保留微信小程序载体、项目配置和可迁移资产
≠ 在旧“文章/轻友动态”信息架构上继续加功能

正式方案：新产品骨架
→ 新用户旅程
→ 新业务 API
→ 新领域模型与业务库
→ 旧内容和身份按规则迁移
```

正式小程序定位为“轻生活体验与习惯陪伴小程序”，围绕以下连续旅程组织：

```text
了解轻生活 → 报名并参与 3/6 日体验
→ 回看我的轻体验 → 选择 14/21 日轻习惯
→ 再次参与或自愿邀请朋友
```

统一档案不要求在轻友端展示一张后台式“客户档案表”，而是把本人资料、活动、体验时间线、付款/卡次、授权和更正能力嵌入上述旅程。

复用边界：

- 可迁移/参考：微信项目配置、OpenID 历史映射、文章与标签、联系方式、部分导航和请求封装。
- 不直接复用：旧三栏导航、动态发布与点赞评论主流程、只靠 OpenID 的身份模型、旧服务端鉴权与旧数据库扩字段方式。
- H5 Demo：只用于需求、文案、视觉和交互验证；正式数据不得只保存在浏览器本地。

### 11.3 对内部工作人员移动端的建议

#### 第一阶段：响应式 H5

- 与 Web 后台同一套产品和权限。
- 快速上线、快速修改。
- 工作人员可在电脑和手机间无缝切换。
- 先用真实使用数据验证语音、拍照和待办频率。

#### 第二阶段：品牌小程序中的授权工作入口

只做高频动作：

```text
最近轻友｜搜索｜语音速记｜拍照｜今日任务
```

不另建第二个重复的小程序，也不复制完整后台。入口仅对带领人或授权工作人员显示，采集数据进入同一新业务 API 和同一轻友档案；服务端仍需按角色、场次和字段再次鉴权。

### 11.4 推荐决策

```text
完整后台：Web
内部移动端首期：响应式 H5
内部高频采集二期：正式品牌小程序中的授权工作入口
正式轻友端：升级版微信小程序
现有 H5：测试 Demo，不作为正式上线端
```

这样既保持正式轻友端的微信连续性，又避免把复杂后台塞进小程序；H5 Demo 的验证成果可以转化为需求和交互依据，但不再决定正式端技术路线。

## 12. 关键业务流程

### 12.1 微信沟通后的语音速记

```text
工作人员聊完微信
→ 打开移动端最近轻友
→ 点击麦克风，口述 20—60 秒
→ 原始录音立即保存
→ ASR 转写
→ LLM 整理事实、自述、待办
→ 工作人员确认
→ 正式入档并创建待办
```

### 12.2 电话后的快速记录

不采集电话录音时：

```text
通话结束
→ 工作人员自己口述摘要
→ 系统记录为“工作人员转述”
→ 不把内容标记为轻友原话
```

如果未来采集实际通话录音，必须另行确认告知、授权、保存期限和第三方处理边界。

### 12.3 一位轻友临时到场

```text
搜索小名
→ 查看档案摘要和卡次余额
→ 选择本期
→ 登记参与与卡次消耗
→ 自动生成时间线事件
→ 轻友端同步显示最新余额
```

### 12.4 上传历史照片

```text
选择期次文件夹/批量照片
→ 建立导入批次
→ 人工关联确认的轻友
→ 合照可关联多人
→ 未识别照片进入待整理
```

首期不做自动人脸确认。

### 12.5 轻友本人补充信息

```text
轻友端进入“我的记录”
→ 选择文字或语音
→ 明确可见范围
→ 提交
→ ASR/LLM 只形成本人自述草稿
→ 本人确认后保存
```

## 13. 隐私、安全与合规边界

轻友档案可能包含医疗健康、声音、照片、交易和未成年人信息。医疗健康信息和不满十四周岁未成年人信息属于敏感个人信息；处理敏感个人信息需要特定目的、充分必要性、严格保护措施和单独同意。[《中华人民共和国个人信息保护法》](https://www.samr.gov.cn/wljys/gzzd/art/2023/art_3ef1e889c1e644d4b65b5f5c7f432386.html)

### 13.1 授权拆分

- 服务履约必要信息。
- 运营联系。
- 敏感健康/身体信息。
- 语音转写。
- 外部 AI 服务辅助整理。
- 匿名化研究或经营分析。

不同意非必要 AI 处理，不应影响基础报名和服务。

### 13.2 外部 AI 服务

- 上线前记录服务商、处理目的、数据类型、保留规则和处理地区。
- 若向境外提供个人信息，需另行评估适用的跨境条件、告知和单独同意。
- 处理敏感个人信息、使用自动化决策或委托第三方处理前，应完成个人信息保护影响评估并留存记录。
- 优先选择可明确关闭训练、支持删除和企业数据协议的服务。

### 13.3 安全控制

- HTTPS。
- 数据库和对象存储访问隔离。
- 敏感字段加密或脱敏。
- 文件使用不可预测的私有地址和短期授权访问。
- API Key 服务端保管和定期轮换。
- 登录失败限制和高风险操作二次确认。
- 数据导出审批、水印和审计。
- 测试环境不使用未脱敏真实数据。
- 备份、恢复演练和安全事件预案。

## 15. 验收标准

### 15.1 轻输入验收

- 从轻友档案发起语音记录，不需要再次选择轻友。
- 录音结束后 2 秒内显示原始材料已保存或明确的离线草稿状态。
- ASR/LLM 失败不丢失录音。
- AI 整理结果可逐项编辑、确认或拒绝。
- 未经人工确认的 AI 内容不进入正式档案摘要。
- 一条普通语音记录从录制到人工确认，建议在 60 秒内完成。

### 15.2 档案验收

- 姓名、小名或手机号搜索后，建议 30 秒内找到目标轻友。
- 同一轻友的活动、交易、卡次、沟通和附件在一个档案中可追溯。
- 同名不同人不能自动合并。
- 期次不明确时进入待核对，不由 AI 猜测。
- 修改关键事实保留原值、原因、操作人和时间。

### 15.3 权限验收

- 普通轻友不能访问他人档案。
- 带领人不能访问未分配期次。
- 财务角色默认不能查看敏感沟通原文。
- 前端无法获得 ASR/LLM API Key。
- 直接调用无权限接口返回拒绝，而不只是隐藏按钮。

### 15.4 AI 验收

准备一组包含以下情况的脱敏样本：

- 正常普通话。
- 小名、期号和数字。
- 长停顿和口语重复。
- 同时包含事实、自述和工作人员判断。
- 包含敏感健康内容。
- 模糊日期或无法判断身份。

验收不是只看转写准确率，还需检查：

- 是否正确分开事实与判断。
- 是否保留原始证据。
- 是否主动标出不确定项。
- 是否避免生成未出现的结论。
- 人工修改是否可追溯。

## 16. 产品指标

### 16.1 效率指标

- 找到指定轻友所需中位时间。
- 新增一条沟通记录所需中位时间。
- 从记录创建待办所需时间。
- 工作人员每周用于重复录入和查找的估算时间。

### 16.2 使用指标

- 每周使用档案的工作人员数。
- 语音、文字、图片三种输入方式占比。
- 草稿完成率。
- 回访任务按时完成率。
- 从期次名单直接进入档案的次数。

### 16.3 AI 质量指标

- ASR 成功率和平均耗时。
- AI 草稿被直接确认、修改后确认、拒绝的比例。
- 各字段平均人工修改量。
- 敏感内容提示命中和漏报样本。
- 每分钟语音和每条记录的平均成本。

不要用“AI 生成记录数量”作为成功指标。真正目标是工作人员更快地留下可信信息。

### 16.4 数据质量指标

- 无明确期次的参与记录数。
- 疑似重复轻友数和处理时长。
- 没有来源或记录人的档案事件数。
- 卡次余额异常数。
- 未经确认的 AI 草稿积压数。

## 17. 实施建议

### 阶段一：先跑通最小记录闭环

```text
轻友搜索
→ 短文字/语音
→ ASR
→ AI 待确认卡片
→ 人工确认
→ 时间线
→ 回访任务
```

H5 Demo 只用于验证，不转为正式生产端；轻友侧功能进入升级版品牌小程序。

### 阶段二：接入业务事实

- 期次与名单。
- 报名与付款。
- 卡次。
- 历史数据导入。
- 通过新业务 API 将本人可见结果接入正式品牌小程序。

### 阶段三：优化移动输入

- 根据真实数据判断哪些高频动作进入品牌小程序的授权工作入口。
- 优化最近轻友、连续录入、语音热词和截图处理。
- 用真实操作时长决定下一轮设计，而不是增加更多字段。

### 阶段四：AI 查询与洞察

- 带证据的档案问答。
- 周期性关系回顾。
- 服务流程分析。
- 21 天陪伴产品验证。

## 18. 上线前必须确认

1. 首批内部使用人员和角色。
2. 哪些字段属于服务必要信息，哪些属于敏感信息。
3. 轻友语音、聊天截图和照片的告知与授权方式。
4. 是否允许第三方 ASR/LLM 处理敏感内容；允许时的服务商和处理地区。
5. 原始语音保存 0、7 还是 30 天。
6. 首期 ASR 和 LLM 服务商、预算上限和降级策略。
7. 桃子等工作人员最常见的 10 条真实输入样例。
8. 工作人员手机型号、微信环境和网络环境，用于内部移动 H5 录音真机测试。
9. 正式品牌小程序首期开放哪些本人档案内容，以及这些能力与小程序升维版本的交付关系。
10. 是否将品牌小程序中的“带领人/工作人员授权工作入口”纳入 9 月 15 日；如不纳入，由内部移动 H5 承担首期采集。
11. 原有小程序线上 AppID、用户、文章、动态、文件和接口的真实迁移范围及回退窗口。
