# 好习惯计划日历规则与实现（2026-09-21）

## 已确认产品规则

- 计划为 14 或 21 个有效自然日，按 Asia/Shanghai 计算。
- 漏打卡不延长计划；最后一个有效日仍可记录，下一自然日进入到期状态。
- 今天暂停，今天不计入。恢复后从被冻结的计划日继续。
- 同日暂停再恢复，该日仍排除；次日继续。同日重复操作不重复扣除日期。
- 暂停前已经写入的当天真实记录保留；从计划完成进度中排除，不删除私人记录。
- 本次不开放卡次核销，余额展示不代表已经交付核销能力。

## 原问题及原因

`QlMiniAppServiceImpl` 读取固定 current_day，既不按自然日推进，也没有服务端暂停/恢复入口。小程序曾使用本地 completedDays，无法跨设备保证真实进度。旧表 paused_at 无法表达多次已结束的暂停区间。

## 修复

- 独立 `QlHabitCalendar` 计算日期，合并重叠/相邻暂停区间，漏记与日期推进解耦。
- 独立 `QlHabitPlanService` 管理开始、推进、暂停、恢复、到期；以轻友行锁串行化操作，计划和暂停区间使用锁定读取，防止事务旧快照导致重复计划或暂停日仍被打卡计入。
- V1_3_12 新增 `ql_habit_pause`；不修改已发布迁移。已有开放暂停根据 paused_at 回填；旧系统没有保存已结束暂停历史，不能凭空恢复。
- 每日记录与计划逐日记录关联；暂停只取消该日的计划完成关联，保留 ql_daily_record。到期按日历判断，不凭空补写完成记录。
- PUT `/habits/{id}/pause`、`/habits/{id}/resume` 使用当前登录轻友及最新计划核验；他人/旧计划拒绝，重复相同操作幂等。
- 小程序读取服务端 completedDays、canRecordToday 和 serverDate；提交失败不显示成功。私人记录缓存键包含计划 ID 和服务端日期，避免暂停后同一个计划日覆盖不同日期的记录。
- 生产启动检查必须存在暂停区间表；漏迁移时拒绝启动。

## 验证与演练

- 7 项纯日历测试：漏记、最后一天/到期、长期暂停、恢复、同日暂停恢复、区间重叠、跨年及 21 天。
- 真实 MySQL 验证：暂停当天已写记录仍保留但不计进度；同日重复暂停恢复；恢复被冻结计划日；自动到期；并发暂停与打卡；并发开始只产生一个计划。初次运行暴露 DATETIME 返回 LocalDateTime 的类型转换问题，修复后通过。
- 小程序全套测试通过；新增暂停恢复、失败不伪成功、重复点击只发一次请求三项行为测试。
- 真实 dev/prod HTTP 测试新增暂停恢复、暂停日拒绝记录、他人计划拒绝操作。最终数量和运行时间见 `habit-validation-results.json`。
- 旧库隔离副本 `qinglife_it_upgrade_r9512d6db45`：迁移前 0 个计划、0 个计划日记录、无暂停表；执行 V1_3_12 后暂停表存在且 0 行。只修改隔离升级副本，未修改 qinglife_test，未重启或部署服务。

## 验收边界

日历推进在查询或操作计划时落库，日期计算保证请求不会使用过期计划继续记录；没有额外后台定时任务。尚未完成微信真机和正式域名验证。整库迁移执行器接管旧库日志、其他依赖风险以及网关实际切换仍需完成，不能据本功能通过便认定整体可上线。
