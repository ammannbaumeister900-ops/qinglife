## S-01｜完成登录修复与生产配置的验收闭环

### 问题点与错误原因

当前登录已改为原子 upsert、行锁及事务内身份绑定，两项 12 路并发测试通过。不能重复报告“当前仍有原死锁”。但 MySQL 集成测试目前是 **7 项、6 通过、1 失败**，生产约束检查的类加载失败尚未解决。

`ProductionConfigurationGuard`、`ProductionSchemaGuard` 仅在 prod profile 启用；公共 `application.yml` 的运行 profile 默认仍是 dev。Maven 使用 prod profile 不等于 Spring 运行时启用 prod。缺少发布入口的硬校验，可能绕过已写好的生产保护。公共配置还有固定 HTTP 图片地址、无限制请求大小设置，prod 存储配置存在模板地址，必须按实际使用的存储适配器核实。

### 证据位置

- `server/api/box-system/src/main/java/com/yicai/life/service/QlWechatLoginService.java`、`QlCustomerIdentityService.java`。
- `server/api/box-web/src/main/resources/application.yml`、`application-prod.yml`。
- `server/api/box-web/src/test/java/com/yicai/web/integration/LoginConcurrencyIT.java`；对应 `target/failsafe-reports`。

### 怎么修复

1. 先完成 T-01，恢复现有 7 项测试；不要跳过失败项。随后补“缺失迁移/索引必须拒绝启动”的测试，不能提前把尚未添加的测试算入通过数。
2. 在实际发布入口显式设置并验证 `SPRING_PROFILES_ACTIVE=prod`，以完整 Spring 上下文验证缺失密钥、错误 schema、不同管理端点配置写法均按预期失败。
3. 用可控微信响应和真实测试 Redis 验证登录 HTTP 链路：事务失败不发 token、禁用账号不可继续使用受保护业务、过期/撤销 token 被拒绝。保持身份服务加入调用者事务的语义，避免随意改成 REQUIRES_NEW。
4. 对实际启用的存储地址、HTTPS、上传限制和健康检查配置建立发布校验；关闭未使用的适配器。已禁用的监控客户端不能再当作“正在外发数据”的事实。
5. 以 HTTP 验证 actuator、文档、Druid 的匿名与授权访问结果，而不只检查配置文本。

### 验收与分工

现有集成测试全部通过，新增负例有真实失败证据；生产入口遗漏 profile 不能静默进入 dev；凭证不写入日志/仓库。Sol 足够处理框架配置与接口测试；复杂迁移规则交 A-02，机械配置同步交 Terra。

## S-02｜封闭匿名通用下载与 GET 删除入口

**P0；状态：源码已确认，生产可利用性未实测；置信度高。**

### 问题点与错误原因

安全配置仍匿名放行通用下载。`CommonController.fileDownload` 接受 `delete` 参数并在 GET 下载后删除文件；下载路径检查主要限制扩展名和 `..`，不证明请求者拥有文件。对应文件存在且文件名可获知时，存在匿名读取及删除路径。部分异常只记录日志，HTTP 结果也不明确。

证据：`server/api/box-framework/src/main/java/com/yicai/framework/config/SecurityConfig.java`；`server/api/box-web/src/main/java/com/yicai/web/controller/common/CommonController.java`；`server/api/box-common/src/main/java/com/yicai/common/utils/file/FileUtils.java`。

### 怎么修复

1. 移除 GET 的删除副作用；确有删除需求时使用独立写接口并检查授权。
2. 下载使用认证加业务资源授权，或业务明确允许的短时签名链接；不能只把“登录过”当作所有文件的访问权。
3. 服务端根据资源 ID 解析受控文件位置，校验规范化路径位于允许目录；保留确实需要公开的静态资源路径。
4. 返回明确的 401/403/404 等状态，避免异常后假成功。

### 验收与分工

用临时合成文件覆盖匿名、无权限、合法授权、错误路径、文件不存在以及 GET 不删除测试。不要对生产文件做攻击验证。`/app/qinglife/**` 的服务层 token 校验是现有设计，不能因其 permitAll 就整体判定未鉴权。问题局部且修法成熟，Sol 完成；无需 Astra。

## S-03｜明确生产版的真实 API、Demo 和 Legacy 边界

**P0；状态：源码已确认；置信度高。**

### 问题点与错误原因

`business-api.js` 仅在 staging 限制本地地址覆盖；production 仍可能采用 localStorage 覆盖。`runtime.js` 默认 demo、空地址，缺少构建发布校验。多个页面保留本地写入与成功提示，可能让用户误以为已保存服务端数据。`legacy-api.js` 指向固定旧生产域名并包含写接口，不能把整个 Legacy 适配器描述成只读。

证据：`apps/miniapp/config/runtime.js`；`apps/miniapp/services/business-api.js`、`legacy-api.js`、`staff-api.js`；`apps/miniapp/pages/mine-flow/index.js`、`friend-flow/index.js`。

### 怎么修复

1. 明确定义 demo/staging/production 的配置契约；生产包必须有允许的 HTTPS 源站，不允许运行时任意覆盖，配置缺失时明确失败。
2. 生产业务入口只走真实接口；尚未实现的能力明确不可用，不能回退本地成功。Demo 作为独立可识别模式保留。
3. 为 Legacy 列出实际允许的读写接口、token 来源和迁移安排；禁止意外复用与当前业务无关的 token。
4. 提供统一有效源站解析函数；图片下载的机械改造交 T-02。评估登录并发请求共用正在执行的登录 Promise，避免重复 wx.login；仍由后端保证幂等。

### 验收与分工

验证三环境打包结果、错误地址、无网络、401、后端失败和本地缓存污染；生产版不能静默显示假保存。Sol 定义边界和联调，Terra 实施固定配置与调用点替换；无需整体重写项目。

## S-04｜统一真实参与记录与老学员、邀请资格判断

**P0；状态：源码规则冲突已确认；置信度高。**

### 问题点与错误原因

小程序 Mapper 的完成体验/完成期次统计主要依赖“报名 confirmed + 期次 completed”，没有以实际出勤为前提。前端 context 也据此合成 completed，影响老学员展示与后续判断。客户档案已有基于出勤及历史参与记录的口径，形成同一客户在不同入口结论不一致。

证据：`server/api/box-system/src/main/java/com/yicai/life/mapper/QlMiniAppMapper.java` 的 `countCompletedExperience`、`countCompletedSessions`；`QlCustomerDossierService.java` 的参与统计；`apps/miniapp/services/business-api.js` 的 context；`apps/miniapp/utils/discovery.js`。

### 怎么修复

1. 依据已存在的 V1.3.9 参与口径，与 A-01 确定的资格/价格契约统一查询；服务端返回权威资格和必要依据，前端不再自行推断。
2. 明确每日出勤与历史参与记录的去重优先级，避免同一期次重复计数。
3. 保留历史报名价格、付款快照；不能因为新查询口径就追改已结算金额。若要求追溯重算，转 A-02 单独设计。

### 验收与分工

覆盖已付款未到场、期次结束但缺席、迟到/早退、一天参与、多天重复出勤、历史参与记录、陪同人、未成年人边界。分别断言后端资格、前端展示及新报名报价一致。规则已有依据，常规 SQL/API 修复交 Sol；复杂历史重算才用 Astra。

## S-05｜补齐每日记录和习惯计划的服务端约束

**P1；相关功能上线时阻断；状态：源码已确认；置信度高。**

### 问题点与错误原因

`saveDailyRecord` 主要检查枚举，客户端仍能传 recordDate、sessionId、planDay；“today”接口未完整约束当天、本人期次和计划天数。`startHabit` 接受 startedAt/sessionId，已有计划返回及日期推进规则不完整。表里没有直接保证每客户仅一个活动计划的约束，但当前身份行锁可能已串行化部分入口，不能未经复现就断言同账号一定产生重复计划。

证据：`QlMiniAppServiceImpl.java` 的 `saveDailyRecord`、`startHabit`；`QlMiniAppMapper.java` 的每日 upsert 和计划写入；`server/migrations/V1_2_0__miniapp_backend_support.sql`；上述两个习惯页面。

### 怎么修复

1. 服务端按明确业务时区计算 today；校验期次归属与适用阶段，planDay 根据实际计划推导或验证。
2. 若允许补录，单独定义补录权限和日期窗口，不与 today 接口混用。
3. 定义暂停、恢复、完成与当前天数推进；保持每日记录、计划天记录及汇总一致。页面改用真实接口，接 S-03。
4. 覆盖所有创建入口后选择事务锁/唯一约束保证一个活动计划；数据库变更先遵循 A-02 规范。

### 验收与分工

覆盖跨日、14/21 天边界、越界 day、其他客户期次、伪造日期、重复提交、暂停恢复、多入口并发。Sol 完成标准状态约束；只有出现未定义的产品规则时提出具体选择，不把整包自动升级 Astra。

## S-07｜建立真实全栈回归和最终发布验收

### 怎么修复

1. 使用 A-02 的可复现数据库基线、测试 Redis 与真实 Java HTTP 服务，贯通小程序适配器和后台接口。
2. 按 A-01 状态表覆盖新老学员、陪同人、最后名额并发、重复报名、付款/退款/取消冲突和事务失败；卡次在上线范围内时纳入 A-03 用例。
