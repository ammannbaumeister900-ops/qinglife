## A-01｜统一三端报名、名额与结算状态转换

**优先级：P0。状态：源码已确认，跨端运行复现待补。问题置信度：高。模型：Astra High；事务设计阶段 XHigh。**

### 证据位置

- [后台报名服务](F:/轻生活项目/轻生活/qinglife/server/api/box-system/src/main/java/com/yicai/life/service/impl/QlRegistrationServiceImpl.java:60)：`insertByBo`、`updateByBo`、`changePayment`、`changeBatchPayment`。
- [小程序报名服务](F:/轻生活项目/轻生活/qinglife/server/api/box-system/src/main/java/com/yicai/life/service/impl/QlMiniAppServiceImpl.java)：`register`。
- [工作人员服务](F:/轻生活项目/轻生活/qinglife/server/api/box-system/src/main/java/com/yicai/life/service/QlStaffWorkspaceService.java)：`enroll`、`capacity`、`confirm`、`payment`、`cancel`。
- `server/api/box-system/src/main/resources/mapper/life/QlRegistrationMapper.xml`；`QlRegistrationBo.java`；`QlRegistrationController.java`。

### 问题与原因

1. 后台新增只验证期次存在和报名状态枚举，未在该调用链内检查期次开放状态、报名窗口、容量或锁定期次。Controller 的参数校验和防重复提交不能替代这些业务约束。
2. 小程序把 `pending + confirmed` 计入占用；工作人员 `capacity` 只统计 `confirmed`。同一名额在不同入口使用不同口径。
3. 后台更新只限制目标枚举，没有完整的前后状态转换条件。源码允许提交从取消到确认、从已付款确认到取消等组合；没有同步定义名额、整单结算、到场和审计的后果。
4. 付款核心已有足额校验和行锁，不能重报“少付款直接结清”的旧缺陷；但外围规则仍分散：工作人员要求金额大于零、限定付款方式，后台核心允许零金额且仅检查付款方式非空。应明确免费期次及可用付款方式，而不是分别打补丁。
5. 多人订单、单人报名、取消、撤销付款之间存在共同锁对象。若只把代码搬进一个类，仍可能保留冲突锁序与半更新状态。

### 修复步骤

1. 先建立状态转换表：每个动作列前置状态、名额占用、订单/个人付款、签到、日志副作用和幂等语义。保留 V1.3.10“本期停用改期”的现状，不自行恢复旧入口。
2. 在隔离 MySQL 中补失败用例：满额后台新增、取消后确认、已付款取消、多人单部分状态变化、三端同时竞争最后一个名额。
3. 抽出唯一的报名领域服务。三个入口只做身份解析、权限校验和 DTO 转换；允许的人工例外要显式建模并审计。
4. 为期次、订单、报名定义全局一致的加锁顺序；名额计算与写入在同一事务内。不要预先拍板某一锁序，先检查付款和取消既有路径，再选不会构成等待环的方案。
5. 锁内重新读取状态；所有写入和日志共同提交。请求重试不得重复交易或重复释放名额；变更请求体复用幂等键应明确拒绝。
6. 保留历史金额快照，不在本任务批量重算旧订单价格。参与资格口径交 S-04 实现；卡次规则交 A-03。

### 验收标准

- 同一业务请求经后台、小程序和移动工作台得到一致结果。
- 并发争抢最后一个名额只产生允许数量的占位；失败不留下订单、报名或签到占位残片。
- 已付款/已有到场的状态更正按明确规则拒绝或整体执行，不产生“报名取消但结算孤立”的不明状态。
- 重试、事务回滚、零价/非零价、多人单和权限矩阵均有真实 Spring/MySQL 测试；需要令牌行为的用例接 Redis。
- 保留并重跑此前已通过的足额付款和重复收款断言。

### 为什么用 Astra，哪些工作要降级

难点是**确定跨端共同不变量和事务边界**，不只是新增校验。Astra 输出状态表、锁序与最小核心实现后，DTO/前端适配和大部分测试可交 Sol；枚举文案与固定字段映射可交 Terra。不可把整个前后端重写都留给 Astra。

## A-02｜建立可重放、可拒绝冲突的数据库迁移基线

**优先级：P0。状态：源码及仓库结构已确认；历史数据冲突是否实际存在未知。问题置信度：高/历史数据未知。模型：Astra High，迁移兼容性难点 XHigh。**

### 证据位置

- [核心迁移](F:/轻生活项目/轻生活/qinglife/server/migrations/V1_1_0__qinglife_core.sql)：依赖既有 `sys_user` 等表。
- [登录唯一约束迁移](F:/轻生活项目/轻生活/qinglife/server/migrations/V1_3_11__wechat_login_identity.sql)：OpenID 二进制排序规则和唯一索引；尚未纳入统一版本执行机制。
- `server/api/box-system/src/main/resources/db/migration/V1_3_10__disable_reschedule.sql`：位于另一套目录；本轮未发现相应 Flyway/Liquibase 依赖或自动加载器。文件存在不证明执行过。
- `ProductionSchemaGuard.java`、`QlCustomerIdentityService.java`。
- `docs/operations/baseline-comparison-20260915.json`：历史数据库目录另有未入主线的导入工具与契约测试。

### 问题与原因

1. 仓库以旧数据库为前提，但没有足够清晰的纯结构初始化入口；不能证明新环境仅靠仓库就能完整初始化。
2. 迁移分散在顶层和应用资源目录；`ql_schema_migration` 的记录方式并不统一，V1.3.11 直接执行 `ADD UNIQUE KEY`，重复执行会失败。不能把这种失败简单理解为“改成 IF EXISTS 即可”。
3. 现有登录迁移在干净合成表上已执行，但未证明适配完整旧表、历史重复身份、排序规则、已有索引和中途失败恢复。
4. 档案唯一性涉及多个旧账号、手机号、OpenID、同名人以及冲突记录。不能以删除重复行、按手机号合并或无条件 `INSERT IGNORE` 使迁移“通过”。
5. `ProductionSchemaGuard` 只检查身份相关条件，不能替代整库版本、约束与迁移历史检查。

### 修复步骤

1. 提取必要的**纯表结构和无个人信息的初始化数据**；原历史 SQL 含业务数据，禁止整份复制进 Git。
2. 选定一个迁移主入口与版本记录规则，列出 V1.1 至当前的真实顺序、依赖、校验和、已执行识别方式；已有文件移动前检查部署脚本依赖。
3. 设计迁移前检查：身份重复、无效外键、OpenID 大小写/尾空格、字段长度、孤立卡次和付款关联、已存在索引。输出可人工核对的冲突清单，不自动猜测合并。
4. 明确失败后的状态：哪些 DDL 原子执行、哪些步骤已提交；如何重新运行、如何恢复备份。不要承诺 MySQL 多条 DDL 可以靠一个普通事务整体回滚。
5. 分别演练空库初始化、旧版本升级、重复执行、故意冲突、中断恢复；检查实际元数据和业务样例关联，不只读取“迁移成功”日志。
6. 如人工解决身份冲突，保留旧值、新值、操作人、理由和关联变化。工具迁入和路径整理交 Terra，规则明确后的执行器与集成测试交 Sol。

### 验收标准

- 新机器用仓库说明能搭出无真实用户数据的环境。
- 迁移漏执行时，生产进程拒绝启动且不会打印密钥。
- 冲突输入使迁移明确失败；重复执行不损坏数据；已有正确索引能被识别。
- 一次恢复演练证明能恢复所需表结构与关联记录。
- 审计报告明确区分“历史数据不存在冲突”和“尚未拿到数据验证”，不得混写。

### 为什么用 Astra

这是旧系统身份语义、数据库约束和发布顺序的联合决策。单纯整理 SQL 文件、执行既定命令不需要 Astra，完成规则设计后必须降级。

## A-03｜补齐卡次消耗、撤销与报名结算关联

**优先级：若本次上线包含卡次登记则 P0；否则必须显式列为未交付能力。状态：能力缺口，非已复现错扣。置信度：中高。模型：Astra High。依赖：A-01、A-02。**

### 证据位置

- [卡次结构](F:/轻生活项目/轻生活/qinglife/server/migrations/V1_1_0__qinglife_core.sql)：`ql_pass_account`、`ql_pass_ledger`。
- `QlCustomerDossierService.java`：按流水汇总余额、判断有效期。
- `QlStaffWorkspaceService.java#passes`、`QlStaffWorkspaceController.java`：只读展示。
- 本轮搜索生产 Java/Mapper/前端代码，未找到 `ql_pass_ledger` 消耗写入链路或完整核销 API；不把 Mock/历史导入脚本算作正式核销功能。

### 问题与原因

现有表结构和余额展示不能完成工作人员登记使用卡次的业务。流水有非零、消耗关联期次等约束，但没有证明请求幂等、账户余额锁、撤销指向原消耗、多人报名与付款关系等规则已实现。

### 修复步骤

1. 先根据已确认范围确定卡类型可用项目、有效期、生效时间、一次报名消耗几次、谁能更正，以及现金与卡次能否混用。缺少规则时先把条件和选项列清楚，不自创业务规则。
2. 以不可直接覆盖的流水为事实来源；通过账户锁和同事务余额校验防止透支。
3. 设计业务唯一键/幂等键，将消耗关联具体报名或核销业务；一项撤销必须指向原流水，不能靠任意正数调整掩盖错扣。
4. 统一登记、撤销、取消报名和现金结算的关系，并记录操作者、原因、时间。
5. Astra 只交付规则、约束和核心事务设计；Sol 实现 API 及两端业务操作；Terra 处理已定字段的展示和文案。

### 验收标准

余额 1 次时并发两次核销最多一项成功；同请求重试只记一条消耗；重复撤销不增加余额；过期/作废账户拒绝；失败不留下报名或流水半状态；账面余额能逐笔对回原始流水。三端展示一致，付款金额不因卡次展示被错误覆盖。

## 3. 执行顺序与升级边界

1. **T-01** 先修测试入口，不消耗 Astra。
2. **S-01/S-02/S-03/S-04** 处理有明确边界的上线问题；A-01/A-02 可先输出规格，但同一文件的实现任务应串行。
3. A-01/A-02 的核心决策落定后，外围实现降至 Sol/Terra；卡次在范围内再执行 A-03。
4. 最终全栈验收由 **S-07** 执行。只有发现跨交易/身份/历史迁移的新矛盾，才送 Astra 定向复审，不要求 Astra 重读所有文案和构建日志。
5. 工具额度、下载失败、缺少数据库凭据不是升级模型的理由。两个模型依赖同一工具条件，换模型不会使这些条件自动满足。

每项单独提交或 PR；交付必须包含复现、修改后的业务不变量、实际测试命令和结果、未覆盖范围、数据库兼容性。没有证据，不关闭问题。
